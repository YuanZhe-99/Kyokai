# 线路协议

控制端经由 EasyTier 数据面连接被控端的引擎：TCP 连到被控端的虚拟 IPv4 地址、端口 47310（[networking.md](networking.md)），
或者按地址连接时，用普通 TCP 连到被控端自己的地址（未写端口时为 47310）。两条路径都不可信，所以会话在其上做端到端的认证与加密，两者相同。协议版本为 10（版本 2 加入了 AI 与剪贴板消息，版本 3 加入了会话操作，版本 4 加入了键盘模式的扫描码按键事件与剪贴板中的文件，版本 5 加入了不使用密码的请求，版本 6 加入了被控端唯一的 AI 记录与共享草稿，版本 7 加入了编码清单与查看者的编码，以及被控端统计信息中的编码时间，版本 8 加入了帧确认与视频流描述中的编码器，版本 9 加入了被控端的声音，版本 10 加入了 `hear-sound` 权限与 10 毫秒的声音数据包）。

## 分帧

每帧是 2 字节大端长度加上相应字节（最多 65 535）。前三帧是 Noise 握手消息；之后的每一帧都是一条 Noise 传输消息，其明文
是一个 JSON 文档、一个媒体分片（见下文），或超过一帧的 JSON 文档的一部分：字节 `0x02`、该部分的序号与部分总数（各 u16，大端），
然后是一段内容。一个文档的各部分按顺序到达，一次一个文档，总计最多 4 MiB；其他任何情况都会关闭会话。

## 握手

Noise `XX_25519_ChaChaPoly_BLAKE2s`，前言（prologue）为 `kyokai/session/v1`。双方每个会话都使用新的 X25519 静态密钥，
并通过签名它来证明自己的设备身份。

| 帧 | 方向 | Noise | 载荷（JSON） |
|---|---|---|---|
| 1 | 控制端 → 被控端 | `e` | 无 |
| 2 | 被控端 → 控制端 | `e, ee, s, es` | `host_hello`：协议、产品版本、源码地址、设备密钥、签名 |
| 3 | 控制端 → 被控端 | `s, se` | `client_hello`：协议、产品版本、设备密钥、签名、请求的权限、两个 OPAQUE 凭据请求（或者不带凭据请求、附上控制端的说明 `about`，表示不使用密码而请求同意），恢复会话时还有恢复令牌 |

签名是设备密钥对 `kyokai/noise-static/v1` 加上发送方 Noise 静态公钥所做的 Ed25519 签名。为了知道一个地址上是哪台设备，
控制端发送第 1 帧、读取第 2 帧、检查其签名后关闭连接（`session.identify`）；被控端不会为此保留会话。若被控端的设备密钥推导不出控制端
所拨打的设备 ID，或者与控制端为该 ID 固定的密钥不同，控制端会拒绝它
（[identity-and-access.md](identity-and-access.md)）。`host_hello` 携带被控端的源码地址，由控制端显示（AGPL-3.0 第 13 条）。

## 密码认证

OPAQUE（`opaque-ke` 4：Ristretto255、使用 SHA-512 的 TripleDH、Argon2id）在 Noise 通道内运行，以被控端的设备密钥为服务器标识（记录在任何控制端出现之前就已存在）、
以 Noise 握手哈希为上下文，因此一次登录无法被重放到另一个通道。被控端有两个槽位：临时密码与固定密码；控制端为每个槽位
各发送一个凭据请求，二者都来自用户输入的同一个密码。

| 帧 | 方向 | 消息 |
|---|---|---|
| 4 | 被控端 → 控制端 | `challenge`：每个槽位一个凭据响应；未设置的槽位以伪造记录应答，因此控制端无法得知哪些槽位存在 |
| 5 | 控制端 → 被控端 | `login`：被密码打开的槽位及其凭据终结消息，以及控制端的说明（`about`：别名、厂商、型号、系统）；两个都打不开时不带槽位 |
| 6 | 被控端 → 控制端 | `verdict`：接受并附上授予的权限、恢复令牌和被控端的说明（`about`），或以原因名称拒绝（`password`、`denied`、`timeout`、`busy`、`rate-limited`、`absent`：无人能确认） |

一次失败的 `login` 计为一次失败（[identity-and-access.md](identity-and-access.md)）。密码正确后，若请求在密码授予的权限之内，被控端立即答复，
否则先请它的用户确认（最多 60 秒）再给出结果。不带凭据请求的 `client_hello` 跳过第 4、5 帧：被控端请它的用户确认，并以第 4 帧发送结果。

## 恢复会话

意外断开的连接（不是 `bye`）可在 60 秒内恢复：控制端每 3 秒重新拨号，并发送上一次结果中的令牌。令牌只能使用一次，与控制端的
设备密钥绑定，只保存在被控端内存中，有效期 2 分钟；有效的令牌会让被控端对第 3 帧立即回以接受的结果（相同权限，无需密码与确认，
并附新令牌），并结束它所恢复的会话——被控端可能还没发现那个会话已断开（否则它会一直占着采集与编码器，直到空闲时限；与任何断开之后一样，该控制端启动的 AI 任务会暂停）；恢复从不会因繁忙被拒绝，因为它取代的是那个会话的位置。其他情况回到正常登录。断开时正在传输的内容不会重发。

## 会话消息

结果为接受之后，双方交换 `{"type": …}` 文档：每 5 秒一次 `ping` / `pong`，以及 `bye`。结束会话的一方（会话被关闭，或其引擎停止：
引擎停止前结束所有会话，最多等待一秒）发送 `bye`，并保持连接打开，直到另一方据此结束会话并关闭连接，或 500 毫秒过去：若先关闭，
另一方的下一次写入会失败，它会把连接当作丢失并尝试恢复。15 秒内没有任何帧的会话会被关闭。
视频与输入见“媒体”，AI 任务见其单独一节。

## 媒体

以字节 `0x01` 开头的明文是媒体分片，而不是 JSON：帧号（u32）、分片序号与分片数（各 u16）、标志（第 0 位：关键帧）以及以微秒计的
显示时间（u64），均为大端，之后是帧的一部分。一帧按需拆成若干分片，在另一端重新拼合；较新帧的分片会丢弃尚未拼完的旧帧
（最新帧优先），超过 64 MiB 的帧会被丢弃。会话开始时，控制端发送 `{"type": "codecs", decode, i444}`：它能解码的编解码器（经 Media Foundation 或 VideoToolbox 的
`h264` 与 `hevc`，经 Media Foundation 的 `vp9`，软件的 `vp9-sw`、`av1` 与 `vp8`），以及其中能以全彩解码的（`vp9-sw`、`av1`；旧版本不带此字段）。
被控端回复 `{"type": "codec-offer", codecs}`：它能发送且控制端能解码的编码，按它的顺序；控制端可以用 `{"type": "codec", codec}`
选择其中之一（`auto`，或清单中的名称；其他名称不改变任何东西），并用 `{"type": "audio", on}` 请求被控端的声音（被控端只发给获得 `hear-sound` 的
控制端，以字节 `0x04` 开头的明文，后接一个 48 kHz 立体声、10 毫秒的 Opus 数据包，静音时不发送，发送某帧的一个分片时已在等待的数据包在
该帧下一个分片之前发出，[computer-use.md](computer-use.md)“声音”）；恢复的控制端
会在发送其 `codecs` 之前再次发送查看者的 `quality`、`codec` 与 `audio`。
被控端在第一帧之前发送 `{"type": "video-start", codec, width, height, i444, encoder, hardware}`（`i444` 与 `hardware` 仅在为真时出现；`encoder`：`videotoolbox`、`media-foundation`、`libvpx` 或 `libaom`，由编码器自己报告，测试图案不带此字段）。每帧的最后一个分片到达时，控制端发送 `{"type": "received", frame}`（该帧的编号）；被控端只在未确认的帧少于 3 个时发送新帧，并且只接受对它已发送且尚未确认的帧的确认。控制端可以发送
`{"type": "key-frame"}`（被控端随后重新说明视频流、其显示器与编码清单，并发送关键帧）——即其界面的第一次请求，以及控制端在其队列丢弃帧期间自己的请求
（最多每秒一次）——在拥有 `control-input` 时还可发送 `{"type": "input", event}`。发送视频期间，被控端每秒发送一次 `{"type": "test-delay"}`，控制端以 `reply: true`
回传；被控端还会发送 `{"type": "stats", delay_ms, fps, bitrate, encode_ms}`（`encode_ms`：上一秒各帧从画面到编码完成的平均时间）（[computer-use.md](computer-use.md)）；控制端可用
`{"type": "quality", preset, fps, i444}` 设置画质，其中 `i444` 表示在双方都支持时要求全彩（4:4:4）。有多个显示器时，被控端还会发送 `{"type": "displays", list, current}`（各显示器的位置与尺寸，主显示器在前），控制端可以用
`{"type": "display", index}` 请求另一个显示器。发送视频期间，被控端还会在指针移动时发送 `{"type": "cursor", x, y, visible}`，即以画面比例表示的指针位置；`visible` 表示它是否在所显示的显示器上。拥有 `control-input` 时，被控端在会话开始时发送
`{"type": "actions", ctrl_alt_del, blocked, privacy}`（阻止或隐私模式变化时也会发送），控制端可以发送 `{"type": "action", action}`，其值为 `lock`、`ctrl-alt-del`、`block`、`unblock`、
`privacy-on` 或 `privacy-off`（[computer-use.md](computer-use.md)）。拥有 `clipboard` 时，任一端都会为本端复制的文本发送 `{"type": "clipboard", text}`（最大 1 MiB），为图片发送
`{"type": "clipboard-image", png}`（8 位 RGBA PNG 的 base64，最多 3 MiB、3840×2160）。拥有 `files` 时，任一端用 `{"type": "clipboard-files", id,
files}` 提供本端复制的文件，每个文件为 `{path, size, dir}`（名称之间用 `/` 分隔的相对路径；最多 1000 项、1 GiB）；
另一端用 `{"type": "files-get", id}` 接受，之后可以用 `{"type": "files-stop", id}` 请发送方停止，发送方用
`{"type": "files-cancel", id}` 放弃已被接受的提供（[computer-use.md](computer-use.md)，“文件”）。内容随后以明文发送：以字节 `0x03`
和提供的 id（u64，大端）开头，然后是字节：按顺序依次为该提供的每个文件，每个恰好 `size` 字节；较新的提供取代较旧的。只有在控制端可以查看屏幕时，被控端才发送视频：它的屏幕（以从 `codecs` 中选定的编解码器），或在无法采集的被控端上发送
320×180 的原始 RGBA 测试图案（编解码器 `raw-rgba`）。

## AI 任务

| 消息 | 方向 | 需要 | 作用 |
|---|---|---|---|
| `{"type": "ai-start", key, instruction}` | 控制端 → 被控端 | `run-ai-task` | 为该控制端在被控端上启动任务；重复的 key 只启动一个任务 |
| `{"type": "ai-command", id, command, text}` | 控制端 → 被控端 | `run-ai-task` | 对被控端的任务执行 `pause`、`resume`、`cancel` 或 `reply`（带 `text`），无论由谁发起 |
| `{"type": "ai-decide", id, approve}` | 控制端 → 被控端 | `approve-ai-action` | 答复被控端任务的批准请求 |
| `{"type": "ai-draft", text}` | 双向 | `run-ai-task`（控制端 → 被控端） | 下一条指令的草稿：控制端的草稿发给被控端，被控端把共享草稿（任何人最后输入的内容）发给每个控制端 |
| `{"type": "ai-task", task}` | 被控端 → 控制端 | — | 被控端最新的任务，无论由谁发起，每个控制端看到的都相同；在它变化时以及会话（重新）开始时发送；带最近 20 个操作与 3 条进度说明 |
| `{"type": "ai-error", error}` | 被控端 → 控制端 | — | 请求被拒绝的原因 |

重新连接后命令绝不会重发；被控端改为发送当前的任务。拥有 `control-input` 的控制端发来的输入会在注入之前暂停正在占用桌面的任务（接管）；
任务执行期间，单纯的指针移动会被丢弃。控制端的引擎把 `ai-task`、`ai-error` 与 `ai-draft` 作为媒体包 5、6 与 10 交给界面；与统计（包 4）一样，较新的任务会替换仍在等待的那个。

## 解码

每一帧在读取前检查大小、在解析前先解密，并解析为固定类型；未知的消息类型会关闭会话。协议带版本号：版本不符时以原因关闭
连接。
随机化测试向两端输入垃圾数据、错误分帧和截断的数据（也包括在真实的首条握手消息之后），以及损坏的身份备份：每个连接都会结束，
不会 panic，损坏的备份也从不改变身份。
