# 电脑操作

控制端如何看到并操作被控端，以及被控端的 AI 如何操作它（Phase 3 手动控制，Phase 4 AI 任务）。

## 视频

| 阶段 | 位置 | 内容 |
|---|---|---|
| 采集 | 被控端引擎 | 通过 RustDesk 的 DXGI 桌面复制采集一个显示器——除非查看窗口选择了其他显示器，否则为主显示器（`core/third_party/rustdesk-dxgi`）；桌面复制无法打开该显示器或 DXGI 未列出任何显示器时（无 GPU 输出、部分虚拟机与远程会话）改用其 GDI 采集器（改用 GDI 的采集在 DXGI 列出该显示器时每 2 秒重试一次桌面复制，因为它在 UAC 提示前后会短暂失败）；屏幕静止时不产生帧（桌面复制的等待超时，GDI 把每张画面与上一张比较），这从不算作显示器丢失 |
| 缩放与转换 | 被控端引擎 | 桌面复制的画面由 GPU 缩小到 1920×1080 以内，边长为偶数，旋转的显示器也在画面离开 GPU 之前转正（着色器每个像素取四个双线性采样，4K 缩到 1080p 时正好是 2×2 的平均，`dxgi/scale.rs`），经按尺寸保留的一个暂存纹理传出：4K 时传到 CPU 的是 8 MB 而不是 33 MB，与 ScreenCaptureKit 交给 Mac 被控端的画面一样。GDI 的画面、保存在系统内存中的桌面图像以及着色器失败的 GPU 由 CPU 取最近的像素缩放（每列、每行的来源在尺寸不变时只计算一次；不缩放的画面逐行转换）。然后 BGRA 转为 Media Foundation 与 VideoToolbox 用的 NV12，或 libvpx 与 libaom 用的平面 I420（全彩时为 I444）——BT.601，有限范围 |
| 编码 | 被控端引擎 | 通过 Media Foundation 编码 H.264：若 GPU 的编码器（异步转换器，在它请求输入时送入系统内存中的 NV12）能在最初 30 个黑帧内产生输出则用它——每个进程只用一个，视频流结束时将其关闭；其他视频流使用软件编码器，取代另一个视频流的视频流（换显示器、换编解码器、切换全彩、恢复的会话）会等待旧的视频流放开它，最多一秒——否则用 Microsoft 的同步软件编码器；低延迟（在设置媒体类型之前设置；第一帧之后就有输出）、CBR 4 Mbit/s、无 B 帧、每 4 秒及按需生成关键帧；30 fps。与 VideoToolbox 从它的缓冲池取画面一样，画面直接转换进最多 4 个输入样本之一，每个样本在它承载的帧输出之后才再次使用（由输出的时间判断；画面重复时若它的样本仍在转换器中，则放入一份副本），要求调用方提供输出样本的转换器每次得到同一个样本，并清除其属性：除转换本身外，每帧不再分配或复制 |
| 编码（macOS） | 被控端引擎 | 通过 VideoToolbox（`core/kyokai-core/src/vt.rs`）编码 H.264 与 HEVC：要求使用硬件编码器，并在它支持时使用低延迟码率控制（它的低延迟编码器 `rtvc` 在硬件上运行，尽管 VideoToolbox 的编码器列表称其为软件：在 M1 上两种方式 1080p 每帧都是 8 毫秒，其中 2 毫秒是我们自己的转换占用的 CPU，2026-10-18），然后不用低延迟，没有硬件时用任何编码器；实时模式、不重排帧，平均码率加上任一秒内不超过其 1.5 倍（静止画面之后的画面仍然较小），每 4 秒及按需生成关键帧；输入来自会话像素缓冲池的 NV12，输出 Annex B，每个关键帧前带参数集，与 Media Foundation 编码器的输出相同（`annexb.rs`） |
| 编码（软件） | 被控端引擎 | 通过 libvpx 编码 VP9（`vp9-sw`）与 VP8，通过 libaom 编码 AV1——使用 RustDesk 的封装（`core/third_party/rustdesk-codec`）与设置：实时模式、按基础码率的 RustDesk 画质系数进行 CBR、每 4 秒及按需生成关键帧；VP9 profile 1 与 AV1 profile 1 承载 4:4:4 |
| 传输 | 会话 | 媒体分片在 Noise 通道中传输（[protocol.md](protocol.md)）；最多只有一帧等待会话：采集循环只在会话有空位容纳下一帧时才取画面——空位由确认腾出，会话把它告诉采集（助手则连同帧率与码率告诉其代理）——因此发出的是最新的画面，而不是在网络后面或为确认等过的画面。被控端最多领先控制端的确认 3 帧（`received`，在每帧最后一个分片到达时发送），因此在慢速路径上（每秒只能传几百 kbit 的中继），帧在采集处等待，而不是在传输的缓冲区中堆积，画面与延迟探测只落后一个往返时间，而不是几秒。每个控制端都通过有序、可靠的流确认每一帧，因此确认迟到意味着路径慢，从不意味着帧丢失：被控端无论多久都等待确认（断开的连接会在 15 秒的空闲时限时结束），并在 5 秒后记录一次“路径慢”（像 RustDesk 的有界等待那样在 3 秒后把帧视为丢失，会每 3 秒再往一条还没送达上几帧的路径上发送三帧与一个新的关键帧；在每秒几百 kbit 的路径上，积压无限增长，延迟达到数秒，画面冻结，输入暂停，会话大约每 25 秒断开并恢复一次）。会话把分片交给它自己的写入器，写入器把输入、确认、声音与会话的其他消息排在等待中的视频分片之前发送（[protocol.md](protocol.md) 的“会话消息”）。助手会话代理的帧按其采集速度到达，得到与被控端领先帧数一样多的位置；找不到位置的帧会被丢弃，其后的帧也一直丢弃到下一个关键帧，并请代理发送关键帧，在丢弃期间每 250 毫秒再请求一次（找不到位置的关键帧也算） |
| 转发 | 控制端引擎 | 会话的媒体队列 → 本地 API 的 `session.media`；落后 3 帧的界面会丢弃正在等待的帧（其中最新的关键帧除外）以及其后直到下一个关键帧的帧（缺少前面的帧就无法解码），控制端会向被控端请求关键帧，在它到达之前每秒再请求一次，用它自己的计时器（静止的屏幕不发送任何可等的东西） |
| 解码 | 界面 | 界面自己加载的核心（`kyokai_decoder_*`）：`h264`、`hevc` 与 `vp9` 用低延迟模式下 Media Foundation 的解码器（H.264 用 Microsoft 的，HEVC 与 VP9 用应用商店的视频扩展；HEVC 以及 GPU 有 H.264 解码器时的 H.264 经 Direct3D 11 在 GPU 上解码，与 Mac 用 VideoToolbox 解码两者一样），NV12 转为 RGBA，并裁剪为视频流的尺寸，像读取 VideoToolbox 的像素缓冲一样直接在解码器的缓冲区中读取（GPU 表面按其自身的行距映射）；在 macOS 上 `h264` 与 `hevc` 用 VideoToolbox；`vp9-sw`、`vp8` 与 `av1` 用 libvpx 或 libaom，I420 或 I444 转为 RGBA。经 Media Foundation 的 VP9 用软件解码（它没有 Direct3D 设备）；每个解码器都会说明它是哪一个、是否用硬件运行（`kyokai_decoder_info`） |
| 显示 | 界面 | 查看窗口的位图来自三幅画面：正在显示的、等待主线程的最新解码画面，以及下一帧要解码进去的；解码从不等待绘制，尚未绘制的画面会让位给更新的画面，新视频流的画面在其第一帧到达之前就已准备好 |

有帧滞留在编码器中时，被控端会重复上一幅画面，使其在屏幕静止时也能输出。请求的关键帧会一直保持请求状态，直到真的输出一个：
屏幕静止时为它重新编码上一幅画面，并每半秒再向编码器请求一次（Media Foundation 的异步编码器可能用它滞留的帧来回应；它会稍等
自己这一帧的输出，其错误事件 `MEError` 算作失败）。接收画面却 2 秒没有任何输出的编码器也算失败：GPU 的编码器在显示器关闭期间
可能不输出，并在显示器恢复后仍无输出（ARM64 测试电脑上的 Qualcomm 编码器：[platform-notes.md](platform-notes.md)），因此视频流只在
系统报告显示器开启时使用 GPU 的编码器——变暗的显示器会先被唤醒并等待 2 秒，第一次查看会等待 Windows 对显示器状态的第一次报告——否则使用软件编码器，并在显示器开启后回到 GPU。
失败的编码器会连同它收到与输出的内容记录日志，并（连同显示器，以取得第一幅画面）重新打开（GPU 的编码器在显示器开启时失败的，
改用软件编码器）；在关键帧发出之前再次失败会结束视频流。视频流结束，或采集以其他方式结束（助手模式下，代理离开，或采集线程
无法跟随输入桌面）时，由会话的画面恢复接手。

被控端从不放弃画面。它的会话监视视频流：帧结束、打开时找不到显示器、编码器或代理、本应有帧却 5 秒没有帧（从开始或请求关键帧起算；3 帧都在等待确认时不算，因为这些帧在等待路径，确认腾出空位时重新计时）、
发出关键帧后仍被不断请求的关键帧，以及——来自声明了 `recovery` 的控制端——查看窗口说它没有显示画面（[protocol.md](protocol.md)）。
上一个发出的关键帧尚未确认时，关键帧请求或查看窗口的 `no-picture` 会等待那一个，而不是强制再发一个（在慢速路径上，新的关键帧只会排在它后面）。
每一项都算作故障并采取下一步：立即重新打开视频，然后在 2 秒后重新打开，再改用提供的下一个编解码器，然后显示占位画面，同时在
2、4、8 秒后、之后每 10 秒再尝试真实的采集；每一步有 4 秒生效，之后的故障才算入下一步。占位画面（320×180 的测试图案，`raw-rgba`）
带有原因（`video-start` 的 `placeholder`：显示器休眠、没有显示器、Kyokai Helper 的代理不在、没有编码器、没有共同的编解码器，
或屏幕无法采集），查看窗口显示该原因，而不显示图案。系统报告重新开启的显示器会立即尝试；画面持续到来 10 秒后，计数重新开始。
在系统报告显示器休眠时找不到显示器的打开，会先唤醒它并再次查找（macOS 会把休眠的显示器排除在其列表之外）。无法采集的被控端
（没有交互式桌面，例如服务或 SSH 会话，或 Kyokai 尚不能在其上采集的系统，`cannot-capture`）则一直显示占位画面，不走恢复步骤；没有 Media Foundation 编码器的被控端（Windows N、未安装 Media Foundation
的 Server 版）用软件编码发送。显示器丢失时（显示模式变化、锁屏或 UAC 提示），被控端会释放它，并每半秒重新打开主显示器；
视频流保持原尺寸，新的显示模式被缩放进去（宽高比变化时，画面会被拉伸，直到下一个会话）。在助手模式下，代理会跟随正在接收输入的桌面
（[run-modes.md](run-modes.md) 的“会话代理”），无论采集到什么，采集都会每半秒把该桌面与自己的桌面比较（GDI 会一直复制旧桌面的黑色画面），
并把变化——锁屏、登录屏幕或 UAC 提示的出现或消失——视为显示器丢失；在输入桌面切换期间打开的显示器，或重试桌面复制时不得不移动线程的
GDI 采集，会在新桌面上重新打开。新的桌面复制若一秒内交不出画面（静止的锁屏或登录屏幕不绘制任何内容），则改由 GDI 取得一幅，
2 秒后再尝试桌面复制；无法启动的 GDI 会在一秒后再次尝试，恢复的桌面复制也会得到同样的后备。每种重新打开显示器的失败只记录一次。

有多个显示器时，被控端随视频流发送显示器列表（主显示器在前，其余从左到右），查看窗口按编号提供选择；选择后会在该显示器上重新开始采集，
并把输入与指针移到那里。AI 任务始终使用主显示器。

桌面复制不会把指针画进画面，因此被控端会报告其指针的位置——每秒最多 60 次，只在移动或离开所显示的显示器时报告——查看窗口用一个不拦截点击的小圆环标出它。无论被控端系统是否绘制它的光标，圆环都标出输入落在哪里：没有接鼠标时 Windows 会隐藏光标，只在拖动时显示，圆环曾因此只在拖动时出现。

会话开始时，控制端会说明它能解码哪些编解码器、其中哪些能以全彩解码，被控端在开始视频之前最多等待一秒，只等一次：之后每次打开视频（恢复步骤、
换显示器）都沿用控制端的编解码器（0.6.2 及以前，等待到期后，每当恢复步骤关闭视频它就再次生效，视频随之像对不说明编解码器的控制端那样在主显示器上
打开——在 Mac 被控端上就是“没有共同的编解码器”占位画面，再也不变）。它依次尝试经 Media
Foundation 的 H.264、HEVC 与 VP9（Windows 被控端）或经 VideoToolbox 的 H.264 与 HEVC（macOS 被控端），然后是软件的 VP9、AV1
与 VP8，使用控制端能解码且编码器能打开的第一个——因此没有系统编解码器的被控端或控制端（Windows N）会退回到软件 VP9。控制端的
编解码器到达时，如果被控端有空闲的硬件 HEVC 编码器，HEVC 排在 H.264 之前（Media Foundation 的在引擎进程中检查并在整个会话中保留，
或 Mac 的媒体引擎；之后未通过试编码的 Windows 编码器退回到软件 HEVC 编码器）。Mac 控制端经 VideoToolbox 解码 H.264，以及其媒体引擎
支持时的 HEVC；两个平台的码流都是 Annex B，所以 Mac 能解码 Windows 被控端的码流，反之亦然。
Media Foundation 的 HEVC 与 VP9 编码器和解码器来自 GPU 或应用商店的视频扩展。控制端只在 GPU 上解码 HEVC（Direct3D 11），
并且只在其 GPU 有 HEVC 解码器时才提供 HEVC：Qualcomm 的硬件 HEVC 编码器会把宽于 1024 像素的画面分成宽度不等的图块列，
HEVC 视频扩展的软件解码器接受这样的码流，却从不输出画面。不说明编解码器的控制端（旧版本）得到 H.264。

**编码选择。** 控制端说明其编解码器之后，被控端提供它能发送且控制端能解码的编码（`codec-offer`，按被控端的顺序）：即它有编码器的
编码——Media Foundation 注册的编码器、VideoToolbox 的编码器以及软件编码器。查看窗口的控制栏在“画质”的“编码”下列出它们，“自动”在最前
（只列名称：H.264、HEVC、VP9、AV1、VP8；同时提供 Media Foundation 与 libvpx 的 VP9 的被控端，会被请求使用它排在前面、更好的那一个；统计信息也用同样的名称说明正在使用的编码）。所选的编码排到被控端顺序的最前面，打开
“全彩”且该编码支持时全彩在前，其他编码仍排在其后，因此编码器打不开的编码会像以前一样退回；只有第一选择改变时视频才会重新开始（控制端的编解码器在被控端已用 H.264 开始之后才到达、或切换全彩时也是如此）。
查看窗口在视频流开始时发送它的画质与编码，控制端引擎会保留它们，并在会话恢复时、在发送其编解码器之前再次发送，使被控端按查看者的
选择打开视频（它们是设置，不是输入）。

**全彩（4:4:4）。** 查看窗口的“画质”菜单中有“全彩”一项。打开且控制端能以 4:4:4 解码软件 VP9 或 AV1 时（当前每个版本都可以），
被控端把它们以全彩排在最前（I444：每个像素都有色度，因此一像素宽的彩色文字和线条保持清晰）并重新开始视频；关闭后恢复正常顺序。
全彩比 4:2:0 占用更多带宽与编码时间，视频流描述会注明它已开启（控制栏路径的提示显示 “4:4:4”）。Windows ARM64 上的 libaom 构建时不含其
SIMD 代码（vcpkg 的移植），因此那里的 AV1 较慢；VP9 排在前面。

查看窗口打开时会请求关键帧；被控端随即重新说明视频流、其显示器与编码清单，并开始新的图像组。

与 RustDesk 的客户端一样，查看窗口的读取从不等待解码：一个 goroutine 读取会话的数据包，把帧交给视频 goroutine（在它自己的系统线程上，
解码器绑定在该线程；最多 4 帧排队），把声音交给声音 goroutine（最多 50 个数据包）；被控端的报告由它自己处理。视频队列已满时丢弃该帧，
并丢弃其后直到关键帧的所有帧，只有关键帧能让帧重新通过；查看窗口立即向被控端请求关键帧，在它到达之前每秒再请求一次，解码器
解码某帧失败后也一样（解码器此后只接受关键帧）。因缺少参数集而让新解码器没有得到画面的关键帧，也算这样的失败，而不是等待。
它还每秒查看一次画面：被控端说它发送了帧（统计中的 `frames`；静止的屏幕不发送，0.4.0 的被控端不报告），却 2 秒没有画面到达，
或还没有任何画面到达时，它请求关键帧，并在所显示的画面上显示“正在恢复画面…”；5 秒仍没有画面时，它告知声明了 `recovery` 的被控端
（`no-picture`，附原因：解码错误、仍在等待或画面过时），界面日志为这段时间记录一行。控制端自己的队列为落后的读取方溢出时，
保留正在等待的最新关键帧并跳到它，因此读取方得到一幅可解码的画面，而不是一幅也没有。声明了 `recovery` 的被控端会在统计中说明
它的视频在做什么（`video`：正常、变暗、正在恢复或占位画面），查看窗口显示这一点——屏幕已休眠或已关闭并正在被唤醒、Kyokai Helper
正在准备、画面正在重新开始——而不是猜测；只有被控端说其显示器已变暗或休眠时才提供**唤醒**（较旧的被控端：与以前一样，3 秒没有画面之后）。
被控端说它不会再尝试时（没有共同的编解码器、无法采集的屏幕），或 10 秒没有显示其屏幕的画面时，查看窗口提供**重新连接**：关闭会话并重新拨号，
与连接结束后的重新连接相同，新会话重新开始它的视频。遇到声音队列已满的声音被丢弃。
因此慢的画面从不拖住声音、输入或被控端的报告。

## 画质与带宽

被控端运行 RustDesk 的视频 QoS（`core/third_party/rustdesk-qos`，包括其上游测试）：每秒在视频流中发送一次延迟探测，控制端会立即回传，
因此探测测量的是视频前方的队列，而不只是路径。回传结果、尚未回传的探测以及每秒发送的帧数共同决定帧率（从 15 提升到 30）
和画质系数；编码器的码率是 RustDesk 针对画面尺寸的基础码率乘以该系数（Balanced：0.67，1080p 下约 1.4 Mbit/s），并在运行中
调整。被控端还会每秒报告它测得的延迟以及选定的帧率与码率；查看窗口会显示延迟。

查看窗口的“画质”菜单提供 RustDesk 的预设——更流畅（系数 0.5）、均衡（0.67）与更清晰（1.5）——15、30 或 60 的帧率上限，以及“全彩”；
它们以 `{"type": "quality", preset, fps, i444}` 发送到被控端，设置 QoS 中该查看者的画质与自定义帧率，以及是否使用全彩（见上文）。

RustDesk 的 QoS 不考虑输入：它只根据探测提升帧率，低于预设的常规帧率时每秒加 1，连续三次良好的探测后加 5，从 15 开始。拖动窗口或打字
需要立即得到每一帧，所以在有人输入（按键、点击、指针移动）后的 2 秒内，只要测得的延迟低于 100 毫秒，被控端就按查看者的上限发送，
安静一段时间后的第一次输入会立即生效，而不是等到下一次探测；延迟更高时由 QoS 决定。指针移动与 RustDesk 一样随到随发，只是查看窗口
只保留尚未发出的最新一次移动（最多每 8 毫秒一次），因此路径卡住时不会有过时的移动排在点击前面。

被控端在统计信息中还报告其帧从画面到编码完成用了多久（`encode_ms`，上一秒各帧的平均值；从采集取到画面时算起，因此 Windows 被控端复制到系统内存的时间也计算在内），其视频流描述说明它的编码器以及是否用
硬件运行（`encoder`、`hardware`，由编码器自己报告）。查看窗口数字的提示显示被控端用什么编码、本机用什么解码（例如“HEVC，
VideoToolbox 硬件”；AV1 总是 libaom 软件）、被控端的编码时间、网络延迟（即探测结果）、查看窗口自己的解码与绘制时间，以及帧率与
被控端目标帧率的对比。控制栏在其图标旁说明网络是直接到达该设备（直连）
还是经由服务器（中继，并提示在两台设备上都打开直接连接，[networking.md](networking.md)）。

## 声音

被控端把声音发给获得 `hear-sound`（单独的权限，控制端默认请求，正确密码默认授予）并提出请求的控制端（`{"type": "audio", on}`；查看
窗口在视频流开始时请求，恢复的控制端会再次请求）。共享哪种声音由被控端用户在“访问”的**共享的声音**中选择（界面的 `sound_source`，在
连接引擎时与改变时以 `sound.source` 发给引擎；助手会传给它的代理；正在进行的流立即切换）：本机正在播放的声音，或某一个输入设备
（`sound.devices` 列出它们：macOS 上是 Core Audio 中带输入的设备，Windows 上是活动的录音端点）。`audio.rs` 在 macOS 上通过只带声音的
主显示器 ScreenCaptureKit 流采集本机播放的声音（不含 Kyokai 自己的声音；“屏幕录制”权限即可；显示器睡眠会结束这个流，停止或未能启动的流每 2 秒重新启动一次），通过音频队列采集输入（“麦克风”权限：
两个应用都带有其用途说明与 `audio-input` 授权，选择输入时会请求它）；在 Windows 上通过 WASAPI 采集默认输出设备的回环或输入设备，按其
自身的格式。声音被转换为 48 kHz 立体声（采样率不同时线性重采样，单声道复制为双声道），以 Opus 的低延迟模式、96 kbit/s 编码为 10 毫秒
一包（`opus.rs`，libopus 由 vcpkg 构建；与 RustDesk 相同），静音半秒后不再发送，直到声音恢复（RustDesk 的零值门限）。助手模式下由会话
代理采集与编码，链路传送数据包。数据包作为以 `0x04` 开头的明文与视频并行传输，不计入视频的确认，发送画面期间到来的声音插在其分块
之间；会话落后时丢弃声音（被控端最多等待
半秒，控制端队列中最多 200 毫秒）。查看窗口在自己加载的核心中解码（`kyokai_audio_*`），通过 MyGo 的音频输出播放，并经过抖动缓冲：
开始时以及每次播放断了之后，它先攒够目标再放出声音，之后随到随放。目标从 80 毫秒开始，每当有声音到来时播放却断了一次（超过 300 毫秒
的停顿是被控端的静音，不算抖动）就增加 40 毫秒，最多 400 毫秒，连续 10 秒没有断时减少 10 毫秒，最少 40 毫秒；超出目标 60 毫秒以上
的声音从最早的开始削减到目标，使声音与画面同步。RustDesk 的每个数据包到达即播放，缓冲最多 3 秒，断时用 5 毫秒淡出，缓冲长时间超过
600 毫秒时才削减。控制栏的
**声音**按钮（未选择时打开，按设备保存）停止播放，并请被控端停止采集。在这台 Mac 上（2026-10-18），8 秒的观看收到 386 个数据包，即
7.7 秒的声音，与画面同时到达，输入列表列出了内置麦克风。

## 输入

只有被授予 `control-input` 的会话，查看窗口才会发送输入；被控端会再次检查。

| 事件 | 发送形式 |
|---|---|
| 指针移动、按下、松开 | `{kind: "pointer", action, button（0 主键，1 次键，2 中键）, x, y}`，x 与 y 是相对画面的比例；在画面周围黑边上的按下与移动会被丢弃（画面上的控制栏自己接收），松开总会发送；没有按住按键的移动以 button 0 发送（被控端知道自己按住了什么）。查看窗口最多每 8 毫秒发送一次最新的移动，任何其他事件都会先发送正在等待的移动（见下文“输入是一条流”） |
| 滚动 | `{kind: "scroll", dx, dy}`，以行计（触控板像素 ÷ 40）；`dy` 为正表示内容向下移动 |
| 映射或翻译模式下的按键 | `{kind: "scan", code, down, caps, num}`：按 Windows 的编号给出按键的扫描码（set-1 扫描码，扩展键为 0xE0xx，Pause 为 0xE11D），并附上控制端的 CapsLock 与 NumLock（[键盘模式](#键盘模式)） |
| 文字 | `{kind: "text", text}`：以 Unicode 字符输入，因此由控制端的键盘布局与死键决定（翻译与传统模式） |
| 传统模式：不带 Ctrl、Alt 或 Win、会产生文字的按键 | 不发送：随后会发送它的文字 |
| 传统模式：其他按键与快捷键 | `{kind: "key", key, down, mods}`，按名称发送（`enter`、`f5`、`page-down`、带 Ctrl 的 `c` 等）；只有发送过按下的键才会发送松开 |

被控端用 `SendInput` 注入：在所显示的显示器上做绝对移动（映射到虚拟桌面，因此位于主显示器左侧或上方的显示器也可用），扫描码按键用
`KEYEVENTF_SCANCODE`（0xE0 开头的扫描码带扩展键标志；Pause 按虚拟键），按名称的按键在导航键上带扩展键标志，并按每个按键的需要按下或松开修饰键，每个事件都
标记为 Kyokai 的（`dwExtraInfo`），以便与本地输入区分。不会向 Kyokai 窗口注入任何输入：落点下方是 Kyokai 窗口时丢弃指针的按下与移动，
指针下方是 Kyokai 窗口时丢弃滚轮，Kyokai 窗口拥有焦点时丢弃按键与文字；松开总会放行。只有人的输入在那里也能放行，而且只在被控端用户关闭了“安全”中的“在屏幕采集中隐藏 Kyokai”（`input.kyokai`）、既没有控制端在等待被控端用户答复、AI 也没有在等待批准时；会话按事件判断，助手的代理按随每个事件告知的结果执行。Kyokai 的窗口不参与采集，因此只按焦点检查时，
Kyokai 那个看不见的窗口在前台时，查看窗口与模型能看到的其他窗口上的点击也会被拒绝。会话结束时会松开它按住的一切。格式错误的事件会被丢弃，但不会结束会话。

**输入是一条流。** 路径卡住时，排队等待的输入会迟到，成为一串过时的按键，因此控制端引擎从不让界面等待（`kyokai_media_write`）：
会话无法接收输入时——正在重连，或发送视频的被控端 1.5 秒没有任何消息，或会话的队列已满——指针移动、按下、点击与文字都会因落后而被拒绝并丢弃。
松开从不被拒绝：引擎记着该会话在被控端按住的按键与按钮，无法送达的松开记为欠账。路径恢复且队列为空后，它进行对账：对声明了
`input-sync` 的被控端（[protocol.md](protocol.md)）发送一个 `{"kind": "sync", held}` 事件，说明现在按住的内容，被控端随即松开该会话按住的
其他一切；对 0.4.0 的被控端则重发这些松开本身（此后又按下的除外）。会话重连期间排队的输入与 AI 命令会在恢复时丢弃，从不迟到送达
（被控端改为发送它当前的 AI 任务；其中查看窗口的画质、编码、声音与剪贴板选择会保留），恢复后的被控端会话不按住任何东西：它所替代的
连接在结束时已松开它按住的内容。界面会得知输入是否暂停（媒体包 15），其控制栏显示“输入已暂停——连接跟不上”；查看窗口发往引擎的
队列也从不丢弃松开（队列满时先把它放在一边，排空后再发送）。两端的会话都不等待网络：输入、确认、ping 与被控端的统计排在等待中的
视频分片之前发出，并且无论视频如何都会被读取（先把每帧完整写出再读取的会话，在慢速路径上数秒读不到输入，两个方向都会卡住）。

会话卡住时键盘抓取会让开：会话正在重连、输入暂停超过半秒，或发送视频的被控端 3 秒既没有帧也没有统计时，查看窗口结束抓取，
输入恢复流动后再次抓取；这期间控制端的键盘归它自己（Alt+Tab、Windows 键、它的输入法、其他程序），在画面中输入的内容按传统模式发送，
落后时被拒绝。抓取只在界面最近一秒内读取过按键时才取走按键（停止读取的界面绝不会困住键盘），钩子也从不等待它的锁：界面的调用
占着锁时到来的按键会直接放行。

### 键盘模式

查看窗口提供 RustDesk 的三种键盘模式；在其控制栏的“键盘”菜单中选择的模式适用于所有查看窗口，并由 Kyokai
记住（未选择时为映射）。映射与翻译需要控制端抓取键盘：Windows 上用低级键盘钩子，macOS 上用事件监听（RustDesk 在那里的
抓取也是这样；需要控制端 Mac 上 Kyokai 的“辅助功能”权限，没有时查看窗口以传统模式工作并加以说明）。Mac 的事件监听在查看窗口
抓取期间取走发往 Kyokai 的按键，把 Mac 键码转换为 PC 扫描码，由被控端再映射回来（Command 即 Windows 键）；没有扫描码的按键
（Fn、媒体键）仍归这台 Mac，大写锁定键在 Mac 上只在切换时报告，因此作为一次按下与松开发送。只有 Kyokai 是最前面的应用且查看窗口正在读取按键时，事件监听
才会取走按键（任一条件不满足时放行所有按键）；小窗被隐藏或连接已结束的查看窗口会结束它的抓取；事件监听随其线程关闭并失效（若留在
系统中，会让所有程序的键盘都失灵，直到退出 Kyokai）。macOS 关掉事件监听时，每个事件监听用自己的句柄把自己重新打开；它的运行循环
以半秒为一段运行，段与段之间查看停止标志，因此在它运行之前发出的停止不会丢失（0.6.1 中，正在停止的事件监听可能清掉较新的事件监听
所需的共享句柄，后者一旦被 macOS 关掉就再也打不开；过早发出的停止则让一个事件监听一直运行）。

键盘跟随指针。在映射与翻译模式下，画面显示时，指针位于查看窗口小窗内的任何位置——标题栏、控制栏、剪贴板面板、画面——查看窗口都进行
抓取，画面在此期间保持文字焦点，因此输入的文字与按键送往同一个会话；小窗并排显示时，按键送往指针下方的连接。远程桌面或 VNC 的画面
也一样。指针在小窗之外（侧边栏、主页、窗口之外）时不抓取，按键送往 Kyokai 自己的界面（0.6.1 及以前，抓取在画面边缘就结束，所以指向
控制栏就会结束抓取）。Kyokai 自己的控件需要按键时，抓取让开：设置面板、搜索、+ 选择器，以及小窗的菜单或分屏列表；菜单一打开就结束
所有抓取（菜单在这一帧之后显示，而 MyGo 只告知选中了哪一项，不告知菜单被关闭），抓取随选择或指针下一次在画面上移动而恢复。
只有 Kyokai 的窗口位于前台时，核心才取走按键；在 Windows 上还要求它是指针处最上层的窗口（`WindowFromPoint` 的根窗口就是前台窗口），
因此指针上方的其他程序窗口会把按键取回，抓取按下的按键会在被控端松开。Mac 的事件监听只检查 Kyokai 是否为最前面的应用（NSWorkspace 给出的、macOS 把按键交给的那个应用；0.6.5 及之前用屏幕窗口列表中最前面的普通窗口代替，Kyokai 窗口平铺到半个屏幕时第二个圆点变为琥珀色，按键被放行），指针交由查看窗口的抓取负责
（0.5.4 还要求事件位置处的窗口属于 Kyokai，这要读取屏幕上的整个窗口列表，而其中其他程序与系统的不可见窗口盖住了 Kyokai 的窗口：
查看窗口以为自己在抓取，事件监听却放行了所有按键，于是除非指针在画面之外，Mac 发送不了 Enter、Tab、Delete、Shift 或 Command——
字母与数字仍作为文字到达）。核心每个窗口只保持一个抓取，因此界面记着每个窗口的抓取由哪个
小窗持有，只有那个小窗才能结束它（`App.grabKeyboard`；切换显示的小窗时，刚被隐藏的小窗结束了新显示的小窗刚刚取得的抓取，
而后者仍丢弃窗口自己的按键事件，于是只有文字到达被控端：没有 Tab、Enter、Delete 或 Shift）。画面获得焦点时会接收文字：macOS
只为接收文字的元素把按键变成文字，而传统模式把字母作为这些文字发送（缺少这一点时，Mac 上的字母都无法到达被控端）。传统模式下，
Mac 的菜单会在窗口看到之前取走 Cmd+C、X、V、A、Z 与 Shift+Cmd+Z；它们的编辑命令会重新作为这些快捷键发送。

抓取可能在 Kyokai 不知情时停止取键：事件监听等待过久时 macOS 会把它关掉；另一个程序持有 Secure Event Input 期间（终端的安全键盘
输入、密码提示），macOS 不把任何按键交给任何事件监听；Windows 会移除让它等待过久的低级键盘钩子。因此查看窗口在这些时候重新持有抓取：
它的窗口重新激活时、指针回到它的小窗时、有按键绕过抓取之后，以及核心报告事件监听或钩子已关闭、抓取已不在或属于另一个窗口时。macOS 上
事件监听被重新打开，线程已结束时则重新创建；Windows 上重新安装钩子。本该被抓取取走却到达窗口的按键——映射模式下是所有按键，翻译
模式下是 Enter、Esc、Backspace、Tab、Delete、Insert、方向键、Home、End、Page Up 与 Page Down、F 键以及快捷键——按传统模式的方式
发送，Mac 菜单的编辑命令也一样（回归：这些按键曾被丢弃，于是直到重启 Kyokai 之前，只有字母以文字形式到达被控端）。抓取期间，查看
窗口每秒两次向核心询问抓取的状态（`kyokai_keyboard_state`）：正在取键、事件监听或钩子已关闭、Secure Event Input 及持有它的程序、
另一个窗口的抓取、读取器已不在、另一个程序在前台。映射与翻译模式下，控制栏键盘图标下方的两个点显示这一状态：第一个点在 Kyokai
持有抓取时亮起；第二个点在按键到达抓取时为绿色，按键未到达或最近三秒内有按键绕过抓取时为琥珀色，按钮的提示用普通人能懂的话说明
原因；没有抓取时两个点都是灰色。界面日志记录抓取开始放过按键的时间与原因、恢复取键的时间，以及每个绕过抓取的按键和核心最近一次
报告的状态（仅仅是另一个程序在前台不单独记录：切换程序就会这样）。

控制端的输入法在画面中是关闭的，每种模式下都是如此，远程桌面或 VNC 的画面也一样（MyGo 的 `InputMethod(false)`）：只针对该元素，
且只在它拥有键盘焦点时——Windows 分离窗口的输入上下文（`ImmAssociateContextEx(hwnd, 0, 0)`）并结束正在进行的输入组合，Mac 的按键
绕过输入法——因此按键输入的是键盘布局上的字符，不进行任何组合。焦点离开画面时输入法即恢复；系统的输入法设置从不改变。中文与日文
用被控端自己的输入法输入：在那边打开它（例如按 Win+Space），并使用映射模式。

**交换 Ctrl 与 Cmd**（任一端是 Mac 时显示在控制栏的“键盘”菜单中，按设备记住）在查看窗口发送的内容中交换 Ctrl 与 Cmd（即 Windows 键）：包括按键
的修饰键，以及按位置发送的左右两侧按键。在 Mac 与 Windows 之间未选择时默认打开，因此 Mac 上的 Cmd+C 在 Windows 上是复制，
Windows 上的 Ctrl+C 在 Mac 上也是复制（RustDesk 有同样的开关，默认关闭）。按名称发送的按键在被控端带上它的修饰键，并随它一起
松开，输入文字时不按住任何修饰键（之前快捷键之后修饰键一直按着，随后输入的字母会带上 Ctrl 或 Cmd）。

| 模式 | 在控制端 | 在被控端 |
|---|---|---|
| 映射 | 指针位于画面上方、且其窗口在前台（在 Windows 上还须是那里最上层的窗口）时，核心中的低级键盘钩子在控制端的窗口看到之前按扫描码取走每个按键：Win、Alt+Tab、Alt+F4 与所有快捷键都送往被控端；CapsLock、NumLock 与 ScrollLock 也作用于控制端 | 每个按键按扫描码注入，因此由被控端的键盘布局与输入法决定输入的字符，与 RustDesk 相同 |
| 翻译 | 在当前按住的修饰键下能在控制端键盘布局上产生字符的按键（死键也算；按着 Win，或只按着 Ctrl 或只按着 Alt 时不算）留给控制端，由它的键盘布局输入，并发送其文字；Shift、Ctrl、Alt 与锁定键两边都收到；AltGr 留在控制端；其他按键与快捷键都按扫描码取走。不为输入法扣留任何按键（以前在中文、日文或韩文布局上输入了字符的按键之后，Enter、Esc、Backspace、Tab、方向键、空格与数字键会交给控制端的输入法最多一秒，这期间输入的 Enter 可能丢失） | 文字以 Unicode 输入，其他按键按扫描码注入 |
| 传统 | 如上所述的 GUI 工具包按键事件：没有 Win 键，没有被窗口占用的快捷键，不分左右修饰键，数字小键盘按其含义发送 | 按名称的按键与 Unicode |

抓取到的每个按键都附带控制端的 CapsLock 与 NumLock：与 RustDesk 的输入服务一样，被控端在字母键之前，
若自己的 CapsLock 不同就按一下 CapsLock；在含义受 NumLock 影响的小键盘按键之前同样处理 NumLock。Windows
自行生成的按键（随 AltGr 出现的 Ctrl、小键盘按键前后的 Shift）不会发送；被控端的键盘布局会生成它自己的。
抓取发送过按下的按键，会在其窗口离开前台或指针、抓取结束或模式改变时松开。控制端上其他程序注入的按键——例如另一个远程控制程序正在操作控制端，如 Kyokai 运行在 RustDesk 会话中——与真实输入的按键一样被取走；只有 Kyokai 自己的（带标记）按键与以文字注入的字符（`VK_PACKET`，RustDesk 的翻译与传统模式）不受影响，这些文字会到达画面，并在每种模式下作为文字发送。
钩子在第一次抓取时安装，在最后一次抓取结束时移除。Ctrl+Alt+Del 无法取走（Windows 不让任何钩子看到它）；
“操作”菜单在助手模式下发送它。

### 会话操作

拥有 `control-input` 时，查看窗口还提供 RustDesk 的会话操作；与输入一样，每个操作都会接管被控端的 AI 任务：

| 操作 | 在被控端 |
|---|---|
| 锁定屏幕 | 在用户会话中调用 `LockWorkStation`（助手模式下由代理调用） |
| Ctrl+Alt+Del | 仅限助手模式：助手作为 SYSTEM 服务调用 `SendSAS`；允许服务这样做的策略（`SoftwareSASGeneration`）只在调用期间打开，之后恢复原样 |
| 阻止对方的键盘和鼠标 | 只要有会话持有阻止，低级钩子就吞掉被控端自己的键盘和鼠标输入；Kyokai 注入的输入照常通过。被控端用户可用 Ctrl+Alt+Shift+Esc（同时停止 AI 任务）或任何钩子都看不到的 Ctrl+Alt+Del 解除；会话结束时也随之解除 |
| 隐私模式 | RustDesk 的隐私模式：一个覆盖整个虚拟桌面、可点穿、置顶且不参与采集（`WDA_EXCLUDEFROMCAPTURE`）的黑色窗口，被控端前的人看到的是黑屏，而画面中仍是屏幕内容；它同时阻止他们的键盘和鼠标，解除方式相同。Windows 无法让窗口不参与采集时会拒绝 |

被控端报告 Ctrl+Alt+Del 是否可用、阻止是否生效以及隐私模式是否开启；查看窗口的开关显示的是这份报告，而不是请求。

## 睡眠

有会话连接期间，被控端会让电脑与显示器保持唤醒（在 Windows 上是一个电源请求，在 macOS 上是阻止空闲系统睡眠与阻止空闲显示器睡眠两个电源断言，名称都是“Kyokai: someone is connected”；第一个会话连接时获取，随最后一个会话释放；助手模式下由用户会话中的会话代理在发送视频期间为显示器持有一份，因为 Windows 不理会来自会话 0 的显示请求），因此空闲计时器既不会切断会话，也不会让被采集的显示器变暗。
电脑仍然进入睡眠时，进行中的 AI 任务会暂停（“电脑进入了睡眠”），等待有人恢复它；唤醒后，会话会像任何断线之后一样经由网络恢复。

变暗的显示器和静止的屏幕一样，不给采集任何可发送的东西。采集一秒没有画面（还没有，或其显示器丢失），或 Windows 报告其显示器已关闭一秒
（控制台显示状态，锁屏与否都算）时，会像人的输入那样唤醒显示器——在 Windows 上，在接收输入的桌面上（锁屏也是）用
`SetThreadExecutionState(ES_DISPLAY_REQUIRED)` 加一次绝对坐标的指针移开一像素再移回，标记为 Kyokai 的输入，使被控端用户的
输入监视不把它算进去；在 macOS 上用 `IOPMAssertionDeclareUserActivity`——最多每 5 秒一次，在用户的会话中进行（助手模式下由代理进行）。
在 Windows 上，执行状态会在一秒内打开变暗的显示器（Kernel-Power 的事件 566 记下它，原因 8）；指针移动在接收输入的桌面上一个单独的线程上
进行，因此采集线程保留它自己的桌面。助手的代理不在时请求的唤醒会发给下一个代理。主显示器睡眠，或连接着显示器却没有任何显示器处于活动状态时，
macOS 报告显示器休眠（`CGDisplayIsAsleep`、`CGGetOnlineDisplayList`）；采集、其画面恢复与查看窗口像对待 Windows 的显示状态一样看待它。
被控端说其显示器已变暗或休眠时（较旧的被控端：3 秒没有画面之后），查看窗口会这样提示，有 `control-input` 时还提供**唤醒**：`wake` 会话操作，
立即以同样方式唤醒显示器并请求关键帧；它不接管被控端的 AI，也不受“远程输入不触及 Kyokai 窗口”这一防护的阻挡。没有 `wake` 的被控端
（0.5.1 及更早）改为收到一次 Shift 按下与松开。睡眠或休眠（包括现代待机 Modern Standby）的电脑已被 Windows 断开网络，Tailscale 与 RustDesk 也一样：唤醒它需要网络唤醒（Wake-on-LAN）或外部硬件，不在 Kyokai 的范围内。

## 剪贴板

会话拥有 `clipboard` 时，两端的引擎每秒查看两次各自的剪贴板（在 Windows 上只在其序列号变化时读取），把会话开始后复制的内容提供给对方，
对方将其放到自己的剪贴板上；以这种方式收到的内容不会再被送回。会话开始前剪贴板上已有的内容不会被提供，Kyokai 自己复制的文本（设备 ID、密码：在 Windows 上，
剪贴板的所有者是 Kyokai 的进程）也不会。支持最大 1 MiB 的文本，或以 PNG 发送、最大 3840×2160 的图片（最多 3 MiB；两者都有时优先文本；文件见“文件”）。
在助手模式下不接收来自控制端的图片，因为助手及其代理都有特权，从不解码远程媒体（[run-modes.md](run-modes.md)）。

控制端有多个连接时，只有小窗位于前台的那个——最近使用的 Kyokai 窗口中焦点所在的小窗；那是主页时则没有——交换剪贴板，与 RustDesk 的客户端相同：在本机复制的内容只发给那台设备，也只有那台设备复制的内容会放到本机剪贴板上。小窗不在前台时复制的内容会等待，等小窗回到前台时再发送（在另一个程序中复制，再到那里粘贴）；这期间对方设备发来的内容会被丢弃。查看窗口的**与这台设备共享剪贴板**开关（按设备保存）会完全停止共享：什么都不提供也不接收，进行中的文件传输会结束（`files-cancel`、`files-stop`），重新打开后只发送之后复制的内容。界面在会话的媒体连接上用 `{"type": "clipboard-use", share, front}` 把两者告诉引擎，引擎为该会话保存（包括恢复后的会话），且从不发给被控端，因此线路协议不变；不认识它的引擎照旧共享。被控端一侧不变：它把复制的内容提供给每个获准 `clipboard` 的控制端。

控制端的引擎把经过的内容——文本、PNG 图片，或按提供清单列出的文件——连同其一侧（`from`：`controller` 或 `host`）与时间报告给界面（媒体包 13），界面把它列在查看窗口的剪贴板面板中，最新的在前，最多 30 条，只在内存中：从不写入磁盘，关闭小窗即消失。不读取它们的界面最多保留 8 个等待中的包。

### 文件

拥有单独的 `files` 权限时，在一端复制的文件和文件夹（在 Windows 上即资源管理器的文件列表 `CF_HDROP`）可以在另一端粘贴；
只有 `clipboard` 不传递文件，只有 `files` 也不传递文本。复制的一端列出所复制的内容——遍历文件夹，跳过链接与联接点——并提供每一项的路径与大小：
最多 1000 项、合计 1 GiB，超出的不会提供。另一端再次检查每个路径与限制后立即接受；它拒绝为空、为绝对路径、含 `.` 或 `..`、
含 Windows 名称中不允许的字符（`< > : " / \ | ? *`、控制字符）、以点或空格结尾、指向设备（`CON`、`NUL`、`COM1`、`LPT1` 等）或重复出现的路径。
随后复制的一端以每块最多 64 KiB 的方式逐个文件流式发送内容，按连接能接收的速度读取，因此不会把整个文件放进内存。
接收的一端把它们写入本次会话专用的文件夹（临时文件夹中的 `Kyokai\<random>`），全部到达后把这些文件放到自己的剪贴板上，
以便在任何地方粘贴。新的复制会取代正在进行的传输，发送期间大小发生变化的文件会结束其传输。
会话结束时该文件夹被删除；此前粘贴出去的文件留在粘贴的位置。

内容在提供被接受后立即传输，而不是在粘贴的那一刻：Windows 在粘贴的程序等待时向复制的程序索取延迟提供的数据，大的传输会让它卡住。

在助手模式下，代理读写剪贴板（管道上只传递路径列表），助手在模拟控制台上已登录用户身份的情况下读写文件，
因此以该用户的权限读取，并写入该用户的临时文件夹；没有用户登录时不共享文件。助手只搬运字节，从不解释它们。

## 被控端状态

为某个被控端保存了密码、或保存了该被控端接受过的登录密钥的控制端，会在其主窗口打开时静默查看该被控端的状态，主页隐藏时放慢（[protocol.md](protocol.md)，
“状态查看者”）：这是一个单独的会话，只请求 `see-status`，不承载画面、输入或声音，不在被控端上保持唤醒请求，也不在那里显示横幅。被控端
只在“无需确认即可连接”开启、且正确的密码或密钥在其密码授予的权限之内时才准入查看者——它从不询问其用户，而是拒绝（`denied`）——无人值守时
只接受固定密码或密钥。`see-status` 默认在密码授予的权限之内；在那里关闭后，查看会在下一次采样时结束。被控端在其他会话之外最多服务 16 个
查看者；它们不列在其会话中，不在其受信任设备中留下记录，状态会单独列出它们（`watchers`：`{device_id, about, since}`）。

只要有人在查看，被控端就在自己的线程上每 2 秒采样一次——所有查看者都要求慢速（`pace`）时每 5 秒一次，有查看者要求恢复常速且上次采样已超过
2 秒时立即再采样——并以 `system` 消息把每次采样发给每个查看者：

| 字段 | Windows | macOS | Linux |
|---|---|---|---|
| `cpu` `{usage, cores, user, system}` | `GetSystemTimes`（system：内核时间减去空闲时间） | `host_statistics`（`HOST_CPU_LOAD_INFO`；user 含 nice） | `/proc/stat`（user 含 nice；system 含中断） |
| `memory` `{used, total}` | `GlobalMemoryStatusEx` | `hw.memsize`；来自 `host_statistics64` 的应用内存、联动内存与压缩内存 | `/proc/meminfo`：总量减去 `MemAvailable` |
| `gpu` `{usage}` 或 null | 3D 引擎的 `Utilization Percentage` 计数器（PDH），按任务管理器的方式求和 | 最忙的 `IOAccelerator` 的 `Device Utilization %` | null（尚未读取） |
| `disk` `{used, total}` | Windows 所在的磁盘 | 数据卷 | 主目录所在的文件系统（`statvfs`） |
| `disk_io` `{read_bps, write_bps}` 或 null | `PhysicalDisk(_Total)` 的读写字节计数器（PDH） | 各 `IOBlockStorageDriver` 的 `Statistics`，换算为速率 | null（尚未读取） |
| `net` `{rx_bps, tx_bps, rx_total, tx_total}` | `GetIfTable2`，处于启用状态的硬件接口 | `getifaddrs`，处于启用状态的接口，不含回环 | `/proc/net/dev`，sysfs 中有设备的接口（不含回环、网桥与隧道） |
| `battery` `{percent, charging}` 或 null | `GetSystemPowerStatus` | 电源（IOKit） | `/sys/class/power_supply` 中的第一块系统电池 |
| `uptime_s`、`at` | `GetTickCount64`；被控端的时钟（Unix 毫秒） | `kern.boottime` | `/proc/uptime` |
| `services` | SSH、远程桌面与 VNC 中哪些在其回环地址上、在其用户设置的端口上接受连接，每 30 秒查看一次（[remote-services.md](remote-services.md)） | 相同 | 相同 |
| `offers` | 每个查看者：其密码或密钥无需询问即可授予的权限（“无需确认即可连接”开启时为密码授予的权限，否则为无），使控制端只提供能用的操作 | 相同 | 相同 |
| `ai` | 每个查看者：被控端的 AI 现在能否开始任务（已选择模型，且除非其服务器在被控端上，否则其提供方的密钥存在） | 相同 | 相同 |

控制端界面为它显示的被控端持有租约（`watch.set` `{devices, slow}`，最多 8 个，`slow` 为其中以慢速查看的；主窗口或状态小窗打开时每 10 秒续一次，
主页显示或隐藏时立即续；30 秒后失效）。主页隐藏时——主窗口被设置遮住或显示其他小窗——主页的被控端以慢速查看，主页再次显示时在同一个查看上恢复常速；
关闭主窗口则放开它们（0.6.2 及以前，主页隐藏就放开它们，再次显示时重新拨号每个被控端）。查看会话在开始时以及每当租约的速度改变时把它告诉被控端。引擎只查看声明了 `status`、
且为其保存了密码或可用密钥的最近设备；否则说明原因，不拨号（`unsupported`、`no-credential`）。它像桌面会话一样拨号，从不续接，断开后等待
10 秒，加倍直到 5 分钟；被拒绝的密码会被忘记，查看随之停止（`refused`），`rate-limited` 则等待 10 分钟。状态只在内存中携带结果：
`watching` `[{device_id, state, sample, received_at}]`，其中 `state` 为 `connecting`、`watching`、`no-credential`、`unsupported`、`refused`
或 `offline`，`received_at`（Unix 毫秒）是采样到达本机的时间，这样旧的采样绝不会被当作当前显示。

## AI 任务

任务在被控端上运行，使用被控端的服务商密钥，操作被控端的主显示器。被控端用户在 AI 会话的小窗中（[gui.md](gui.md)，“AI 会话”；或用
`kyokai-svc ctl ai-start`）启动任务。获得 `run-ai-task` 的控制端可以在该被控端的 AI 会话小窗中启动任务，并控制被控端的任务，无论由谁发起（被控端为所有控制端保留同一份 AI 记录），所用的是一个只请求 `run-ai-task` 与 `approve-ai-action` 的独立会话；下一条指令的草稿与被控端用户和其他每个控制端实时共享
（[protocol.md](protocol.md)，“AI 任务”）；拥有 `approve-ai-action` 时还可以答复这些任务的批准请求，而被控端用户也始终可以答复。
同一时间只有一个任务占用桌面，用同一个幂等键启动两次只会启动一个任务。

### 服务商

被控端用户设置**来源**（设置中的 AI；`ai.json`）：每个来源有 id、名称、所用的模板、协议、基础 URL 以及从中使用的模型，任务使用某个来源中
选定的一个模型。新的被控端有两个来源：Claude（`https://api.anthropic.com/v1`）与 OpenAI（`https://api.openai.com/v1`）。模板还可添加 OpenRouter、
Google Gemini、Groq、Together、Fireworks、Deep Infra、Mistral、xAI、Moonshot、Z.ai / BigModel、阿里云百炼、SiliconFlow、火山方舟、MiniMax、
阶跃星辰、百度千帆、腾讯混元、NVIDIA NIM、Hugging Face、GitHub Models、Ollama、LM Studio 与 llama.cpp server（取自 MyApps-AI 的目录，
保留能接收图片和工具调用的 API；有多个站点的服务商按名称提供各站点）；自定义可以使用任意地址与协议。基础 URL 必须是 HTTPS，或只指向本机的明文 HTTP
（`localhost`、`127.0.0.0/8`、`::1`），因为截图会发往那里；这样的本机聊天服务器不需要密钥。每个来源的密钥是机密存储中的 `ai.<id>.key`，
移除来源时其密钥一并删除。**列出模型**只在用户要求时向来源查询模型（`GET <base>/models`；支持 OpenAI 风格、Ollama 与 OpenRouter 的列表，
不含嵌入、语音、图像与审核模型）；不会自行获取任何内容。

| 协议 | 使用者 | 请求 |
|---|---|---|
| `anthropic` | Claude | 带 computer 工具集的 Messages API（见下） |
| `openai-responses` | OpenAI | 带 `computer` 工具的 Responses API（见下） |
| `openai-chat` | 其他所有模板与自定义 | chat completions，把 Kyokai 的操作作为函数工具提供，名称与形式同 computer 工具集的成员（`left_click` 带 `coordinate`、`key` 带 `text`、`scroll` 带 `scroll_direction` 与 `scroll_amount` 等），因此三种协议共用一个解析器；屏幕以图片放在用户消息中，每个调用以一条 `tool` 消息答复，随后附上该批操作之后的屏幕；历史中只保留最新的 3 张截图。模型必须能接收图片并调用工具 |

模型按 OpenRouter 的写法显示为 `厂商: 模型`（`Anthropic: Claude Opus 5.5`、`Qwen: Qwen2.5 VL 72B Instruct`），经由其他来源访问的模型后面附上来源；
名称来自服务商自己的列表，或按规则由 id 得出（MyApps-AI 的命名规则，移植在 `internal/gui/modelname.go` 中）。

| | Claude | OpenAI |
|---|---|---|
| 请求 | Messages API 加 `computer_toolset_20260801`，自适应思考并返回进度说明，effort 为 `high`，服务端回退，输入超过 100,000 token 后由服务端清除旧的工具结果（保留最新 5 个） | Responses API 加 `computer` 工具，`previous_response_id`，`truncation: "auto"`，每次请求都带上指令 |
| 回复 | 每个操作一个 `tool_result`；历史只追加 | 每个调用一个 `computer_call_output`，附上该批操作之后的屏幕，并用一条说明列出失败或未执行的操作；安全检查只在被控端用户批准后才确认 |

请求经 HTTPS 发出（rustls，ring 提供方，系统根证书），每次最长五分钟，遇到过载和服务端错误时重试三次。显示给用户的错误绝不包含密钥。

### 截图与操作

被控端用 RustDesk 的 GDI 采集器按显示器的像素尺寸采集主显示器（采集线程按显示器感知 DPI），用平均法缩放到
1366×768 以内，以 PNG 发送。放大查看会裁剪一次新的采集，且绝不放大。坐标以最近一张完整截图为准；被控端把它们映射到显示器上，
经上文的输入服务注入，同样受 Kyokai 窗口的保护并带有标记，而 AI 永远不能越过这层保护。

| 操作（`kind`） | 字段 | 执行方式 |
|---|---|---|
| `screenshot`、`zoom` | 放大查看时为 `region` | 一次采集，返回给模型 |
| `cursor-position` | — | 指针在截图像素中的位置，以文本返回 |
| `move` | `to`、`held` 键 | 按下修饰键，移动指针 |
| `click` | `at`（或指针位置）、`button`、`count`、`modifiers` | 先移动，再按下并松开（重复时间隔 40 ms） |
| `mouse-down`、`mouse-up` | `button` | 在指针位置按下或松开 |
| `drag` | 点的 `path`、`modifiers` | 按下，每段移动八次、间隔 10 ms，松开 |
| `scroll` | `at`、`dx`、`dy`（每格 120）、`modifiers` | 滚轮格数 |
| `type` | `text` | Unicode 文本，每 30 ms 一个字符（Windows 11 记事本等应用会把更快的连串输入弄乱）；每个换行按一次 Enter |
| `key-combo` | `keys`、`repeat` | 按组合中的修饰键按下各键 |
| `hold-key` | `keys`、`duration_ms` | 按下、保持、松开 |
| `wait` | `duration_ms` | 暂停 |

每个操作之前，被控端会检查：它能被解析；它的点位于最近一张截图之内；它的限制（文本最多 16 KiB，最多重复 100 次，等待和按住最长
300 秒，最多 100 格，拖动最多 256 个点）；屏幕尺寸仍与那张截图一致（否则操作已过时并被拒绝）；以及是否需要被控端用户批准。
第一个失败会结束本轮：其后的操作都回复为“未执行”。每个操作结束时都会松开它按住的一切。

批准方式为“被标记的步骤”（默认）或“每个操作”。前者在服务商为本轮提出安全检查时询问（在本轮第一个操作前询问一次），以及对使用
Windows / Command 键的快捷键询问。被拒绝的操作以“The host user declined this action”失败，模型从这里继续。

### 状态

| 事件 | 起始状态 | 结束状态 |
|---|---|---|
| 暂停（被控端用户、本地输入、控制端、接管，或控制端的会话结束） | running、approval | paused |
| 继续 | paused | running |
| 取消（包括紧急停止） | running、approval、paused | cancelled |
| 操作需要批准 | running | approval |
| 被控端用户作出决定 | approval | running |
| 模型完成 | running、paused | done |
| 出错 | running、approval、paused | failed |
| 被控端用户回复 | done | running |

### 被控端用户永远优先

任务运行期间，低级键盘与鼠标钩子监视本地输入：任务最近一次获得桌面（启动、继续或某个操作获得批准）之后，任何不是 Kyokai 注入的事件。
按键、鼠标按钮或滚轮立即计入；指针移动要在 1.5 秒之后才计入，因此点击“继续”或“允许”后把手移开鼠标不算接管；任务等待批准期间，本地输入不计入。
本地输入会立即暂停正在运行的任务，无论模型正在思考还是操作正在执行；按住的键或按钮会被松开。控制端的人在查看窗口中使用键盘或鼠标时同样构成接管：
在其输入被注入之前任务就会暂停，而任务执行期间单纯的指针移动不会被注入。每次暂停与取消都会推进任务的输入租约：之后才到达的模型响应会被记录，
但其中的操作一个也不会执行；对它的回复要等继续之后才发出，告诉模型什么都没有执行、应先重新截图。取消还会丢弃正在进行的请求。
Ctrl+Alt+Shift+Esc（紧急停止，任务运行期间有效）、托盘中的“停止 AI 任务”以及 `ai.stop` 都会取消任务，停止引擎也一样。

### 历史与设置

状态目录中的 `ai.json` 保存各来源、选定的模型与批准方式（最初版本的文件——一个服务商以及 Claude 与 OpenAI 各一个模型——会读成两个默认来源）；
密钥保存在机密存储中（`ai.<source>.key`），不会再显示，除了发给各自的来源之外不发往任何地方。`ai-tasks.json` 保存已结束的任务——指令、模型的文字与进度说明、各个操作及其结果，绝不包含截图——最多
100 个；设置中的 AI 可以清除它（最近的任务），连同界面保存在 `gui.json` 中的 AI 会话。已结束任务的对话保留在内存中，因此在引擎停止之前，回复可以让它继续。

## macOS

| 部分 | 方式 |
|---|---|
| 权限 | 采集需要“屏幕录制”，输入需要“辅助功能”，本地输入监视需要“输入监控”，另有机密存储的钥匙串项目（[security.md](security.md)）；引擎报告这些权限（状态中的 `permissions`）；图形界面在每个版本首次启动时请求，也可以通过权限卡片上的“允许”请求——隐私权限在图形界面自己的进程中请求（`kyokai_privacy_request`），这样提示属于应用本身，而授予应用的权限同样覆盖引擎（macOS 把引擎算作应用的一部分）；钥匙串经由引擎请求（`permission.request` `keychain`）。macOS 27 对两个进程都不弹出提示：点“允许”会打开相应面板，在其中打开 Kyokai 的开关（“辅助功能”面板在那里称为“设备控制与数据访问”），同时打开系统设置中的相应面板。“屏幕录制”的授权在 Kyokai 重新启动后才生效，权限卡片上的“重新打开 Kyokai”会先停止引擎再重启 |
| 显示器 | Core Graphics 的活动显示器，以点为单位，即其全局坐标的单位（Retina 显示器是其像素的一半）；主显示器即首选显示器 |
| 采集 | 显示器的 ScreenCaptureKit 流，按其像素尺寸缩放到 1920×1080 以内，BGRA，不含指针（查看窗口根据指针消息自己绘制），“安全”中“在屏幕采集中隐藏 Kyokai”打开时（默认）也不含 Kyokai 的进程与应用的窗口：界面在连接引擎时以及设置改变时把它告诉引擎（`capture.show`；助手模式下由助手转告其代理，代理每次启动时也再转告一次），正在进行的视频流按新的过滤器重新打开（约半秒没有画面；原先在原处更新过滤器，只尝试一次，未生效时 Kyokai 一直被隐藏），AI 截图也照此处理；画面不变时不发送；没有 bundle 标识的程序永远不会被当作 Kyokai。没有权限时（在调用 ScreenCaptureKit 之前检查，因此不会等待任何提示）被控端立即显示占位画面（屏幕无法采集）且不发送声音。停止的视频流会记录 ScreenCaptureKit 的错误域与错误码。视频流结束时先移除其输出再停止，最多等待 2 秒；其完成回调让视频流一直存活到 ScreenCaptureKit 答复为止，未能按时答复的启动也以同样方式停止。系统框架的每个回调（画面、声音、VideoToolbox、事件监听器、音频队列）都自行捕获 panic，并记入引擎日志 |
| 编码 | 先用 VideoToolbox 的 H.264 与 HEVC（见上文），然后是软件编解码器（`vp9-sw`、`av1`、`vp8`） |
| 解码 | 查看窗口经 VideoToolbox 解码 `h264` 与 `hevc`，经 libvpx 与 libaom 解码软件编码 |
| 输入 | 在 HID 层投递并标记为 Kyokai 的 Core Graphics 事件：以点为单位的指针事件，带点击次数以支持双击与三击；滚轮刻度按行；按名称的按键与修饰键（`ctrl` → Control，`alt` → Option，`meta` → Command），附带所按住修饰键的标志；文本以 Unicode 输入；扫描码经对照表转换为 Mac 键码（Caps Lock 跟随控制端；Mac 没有 NumLock）。防护会查找该点下窗口的所有者（按键则查找最前面的普通窗口），丢弃发往 Kyokai 任一进程（应用、引擎、Kyokai Helper）的事件，与 Windows 上一样按其可执行文件判断（0.4.0 之前只匹配本引擎及其父进程，在助手模式下由 launchd 启动代理，因而漏掉了应用） |
| 本地输入 | 只监听的事件监听器（输入监控）记录被控端用户的按键与移动，跳过 Kyokai 标记的事件，并监视 Ctrl+Option+Shift+Esc；监听器随其线程关闭并失效，即使在其运行循环开始之前就被丢弃，线程也会结束 |
| AI 任务 | 每次截图用一个短暂的 ScreenCaptureKit 流以全分辨率采集主显示器，输入与监视相同 |

## Linux

| 部分 | 方式 |
|---|---|
| 会话 | 由环境判断：设置了 `$WAYLAND_DISPLAY` 或 `$XDG_SESSION_TYPE` 为 wayland 时为 Wayland，否则设置了 `$DISPLAY` 时为 X11，否则没有；目前只有 X11 能采集和注入（Wayland 被控端显示占位画面，即屏幕无法采集） |
| 显示器 | RandR 的显示器，主显示器在前（没有标记时取最左边的），没有 RandR 时整个屏幕算一个 |
| 采集 | 通过 MIT-SHM 把根窗口中该显示器的矩形读入一个 System V 共享内存段（只有本用户可读，X 服务器挂接后立即删除其名称），按显示器像素大小的 BGRA，不含指针；与上一幅相同的画面不算画面（静止屏幕），每秒最多查看 60 次；位置或大小改变的显示器视为丢失并重新打开。“对采集隐藏 Kyokai”开启时，画面离开采集前会把屏幕上可见的 Kyokai 窗口部分涂黑（每个 Kyokai 窗口减去其上方其他程序的窗口，取自窗口管理器的堆叠列表，没有时取根窗口的子窗口，每 250 毫秒读取一次）；窗口所属进程来自 X-Resource 扩展，没有时取 `_NET_WM_PID`，与其他系统一样按可执行文件判断是否为 Kyokai |
| 编码 | 软件编解码器（`vp9-sw`、`av1`、`vp8`） |
| 输入 | XTest：在根窗口上移动指针与按键，滚轮按整格作为按钮 4–7，命名按键与扫描码经 evdev 码（X 键码为 evdev 码加 8，因此按键输入什么由被控端的布局决定，符合映射模式的要求），Caps Lock 与 Num Lock 在其影响的按键之前跟随控制端；文字经空闲键码（没有 keysym 的键码）输入，每段字符一次性映射，每个字符一个键码，在其按键之前以及键码再次改变之前各留 50 毫秒（X 程序只在下次查键时才读取改变后的映射）。与其他系统一样，保护机制丢弃落在 Kyokai 窗口上的按下（指针处最上层的窗口，按键为活动窗口） |
| 本地输入 | 主设备的 XInput 2 原始按键、按钮与移动事件，不含 XTest 的虚拟设备（Kyokai 自己的输入）；Ctrl+Alt+Shift+Esc 为紧急停止 |
| 显示器电源 | 由 DPMS 判断显示器是否关闭；唤醒时打开 DPMS 并重置屏幕保护 |
| AI 任务 | 主显示器的全分辨率画面，每次截图读取一幅 MIT-SHM 画面，输入与监视相同 |
