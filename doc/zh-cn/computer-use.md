# 电脑操作

控制端如何看到并操作被控端，以及被控端的 AI 如何操作它（Phase 3 手动控制，Phase 4 AI 任务）。

## 视频

| 阶段 | 位置 | 内容 |
|---|---|---|
| 采集 | 被控端引擎 | 通过 RustDesk 的 DXGI 桌面复制采集一个显示器——除非查看窗口选择了其他显示器，否则为主显示器（`core/third_party/rustdesk-dxgi`）；桌面复制无法打开该显示器或 DXGI 未列出任何显示器时（无 GPU 输出、部分虚拟机与远程会话）改用其 GDI 采集器；屏幕静止时不产生帧（GDI 把每张画面与上一张比较） |
| 缩放与转换 | 被控端引擎 | BGRA 转为 Media Foundation 与 VideoToolbox 用的 NV12，或 libvpx 与 libaom 用的平面 I420（全彩时为 I444）——BT.601，有限范围——缩小到 1920×1080 以内，边长为偶数，取最近的像素（每列、每行的来源在尺寸不变时只计算一次；不缩放的画面逐行转换） |
| 编码 | 被控端引擎 | 通过 Media Foundation 编码 H.264：若 GPU 的编码器（异步转换器，在它请求输入时送入系统内存中的 NV12）能在最初 30 个黑帧内产生输出则用它——每个进程只用一个，视频流结束时将其关闭；其他视频流使用软件编码器——否则用 Microsoft 的同步软件编码器；低延迟（在设置媒体类型之前设置；第一帧之后就有输出）、CBR 4 Mbit/s、无 B 帧、每 4 秒及按需生成关键帧；30 fps |
| 编码（macOS） | 被控端引擎 | 通过 VideoToolbox（`core/kyokai-core/src/vt.rs`）编码 H.264 与 HEVC：要求使用硬件编码器，并在它支持时使用低延迟码率控制（它的低延迟编码器 `rtvc` 在硬件上运行，尽管 VideoToolbox 的编码器列表称其为软件：在 M1 上两种方式 1080p 每帧都是 8 毫秒，其中 2 毫秒是我们自己的转换占用的 CPU，2026-10-18），然后不用低延迟，没有硬件时用任何编码器；实时模式、不重排帧，平均码率加上任一秒内不超过其 1.5 倍（静止画面之后的画面仍然较小），每 4 秒及按需生成关键帧；输入来自会话像素缓冲池的 NV12，输出 Annex B，每个关键帧前带参数集，与 Media Foundation 编码器的输出相同（`annexb.rs`） |
| 编码（软件） | 被控端引擎 | 通过 libvpx 编码 VP9（`vp9-sw`）与 VP8，通过 libaom 编码 AV1——使用 RustDesk 的封装（`core/third_party/rustdesk-codec`）与设置：实时模式、按基础码率的 RustDesk 画质系数进行 CBR、每 4 秒及按需生成关键帧；VP9 profile 1 与 AV1 profile 1 承载 4:4:4 |
| 传输 | 会话 | 媒体分片在 Noise 通道中传输（[protocol.md](protocol.md)）；最多只有一帧等待会话：采集循环只在会话有空位容纳下一帧时才取画面，因此发出的是最新的画面，而不是在网络后面等过的画面。被控端最多领先控制端的确认 3 帧（`received`，在每帧最后一个分片到达时发送），因此在慢速路径上（每秒只能传几百 kbit 的中继），帧在采集处等待，而不是在传输的缓冲区中堆积，画面与延迟探测只落后一个往返时间，而不是几秒。助手会话代理的帧按其采集速度到达，多给一个位置；找不到位置的帧会被丢弃，其后的帧也一直丢弃到下一个关键帧，并请代理发送关键帧 |
| 转发 | 控制端引擎 | 会话的媒体队列 → 本地 API 的 `session.media`；落后 3 帧的界面会丢弃正在等待的帧以及其后直到下一个关键帧的帧（缺少前面的帧就无法解码），控制端会向被控端请求关键帧，在它到达之前每秒再请求一次 |
| 解码 | 界面 | 界面自己加载的核心（`kyokai_decoder_*`）：`h264`、`hevc` 与 `vp9` 用低延迟模式下 Media Foundation 的解码器（H.264 用 Microsoft 的，HEVC 与 VP9 用应用商店的视频扩展；HEVC 经 Direct3D 11 在 GPU 上解码），NV12 转为 RGBA，并裁剪为视频流的尺寸；在 macOS 上 `h264` 与 `hevc` 用 VideoToolbox（输出 NV12，同样转为 RGBA）；`vp9-sw`、`vp8` 与 `av1` 用 libvpx 或 libaom，I420 或 I444 转为 RGBA。Media Foundation 在 GPU 上解码 HEVC，用软件解码 H.264 与 VP9（它们没有 Direct3D 设备）；每个解码器都会说明它是哪一个、是否用硬件运行（`kyokai_decoder_info`） |
| 显示 | 界面 | 查看窗口的位图来自三幅画面：正在显示的、等待主线程的最新解码画面，以及下一帧要解码进去的；解码从不等待绘制，尚未绘制的画面会让位给更新的画面，新视频流的画面在其第一帧到达之前就已准备好 |

有帧滞留在编码器中时，被控端会重复上一幅画面，使其在屏幕静止时也能输出。无法采集的被控端（没有交互式桌面，例如服务或
SSH 会话）会改为发送 320×180 的测试图案（`raw-rgba`）；没有 Media Foundation 编码器的被控端（Windows N、未安装 Media Foundation
的 Server 版）用软件编码发送。显示器丢失时（显示模式变化、锁屏或 UAC 提示），被控端会释放它，并每半秒重新打开主显示器；
视频流保持原尺寸，新的显示模式被缩放进去（宽高比变化时，画面会被拉伸，直到下一个会话）。

有多个显示器时，被控端随视频流发送显示器列表（主显示器在前，其余从左到右），查看窗口按编号提供选择；选择后会在该显示器上重新开始采集，
并把输入与指针移到那里。AI 任务始终使用主显示器。

桌面复制不会把指针画进画面，因此被控端会报告其指针的位置——每秒最多 60 次，只在移动或隐藏时报告——查看窗口用一个不拦截点击的小圆环标出它。

会话开始时，控制端会说明它能解码哪些编解码器、其中哪些能以全彩解码，被控端在开始视频之前最多等待一秒。它依次尝试经 Media
Foundation 的 H.264、HEVC 与 VP9（Windows 被控端）或经 VideoToolbox 的 H.264 与 HEVC（macOS 被控端），然后是软件的 VP9、AV1
与 VP8，使用控制端能解码且编码器能打开的第一个——因此没有系统编解码器的被控端或控制端（Windows N）会退回到软件 VP9。控制端的
编解码器到达时，如果被控端有空闲的硬件 HEVC 编码器，HEVC 排在 H.264 之前（Media Foundation 的在引擎进程中检查并在整个会话中保留，
或 Mac 的媒体引擎；之后未通过试编码的 Windows 编码器退回到软件 HEVC 编码器）。Mac 控制端经 VideoToolbox 解码 H.264，以及其媒体引擎
支持时的 HEVC；两个平台的码流都是 Annex B，所以 Mac 能解码 Windows 被控端的码流，反之亦然。
Media Foundation 的 HEVC 与 VP9 编码器和解码器来自 GPU 或应用商店的视频扩展。控制端只在 GPU 上解码 HEVC（Direct3D 11），
并且只在其 GPU 有 HEVC 解码器时才提供 HEVC：Qualcomm 的硬件 HEVC 编码器会把宽于 1024 像素的画面分成宽度不等的图块列，
HEVC 视频扩展的软件解码器接受这样的码流，却从不输出画面。不说明编解码器的控制端（旧版本）得到 H.264。

**编码选择。** 控制端说明其编解码器之后，被控端提供它能发送且控制端能解码的编码（`codec-offer`，按被控端的顺序）：即它有编码器的
编码——Media Foundation 注册的编码器、VideoToolbox 的编码器以及软件编码器。查看窗口的状态栏在“编码”下列出它们，“自动”在最前
（只列名称：H.264、HEVC、VP9、AV1、VP8；同时提供 Media Foundation 与 libvpx 的 VP9 的被控端，会被请求使用它排在前面、更好的那一个；统计信息也用同样的名称说明正在使用的编码）。所选的编码排到被控端顺序的最前面，打开
“全彩”且该编码支持时全彩在前，其他编码仍排在其后，因此编码器打不开的编码会像以前一样退回；只有第一选择改变时视频才会重新开始。
查看窗口在视频流开始时发送它的画质与编码，控制端引擎会保留它们，并在会话恢复时、在发送其编解码器之前再次发送，使被控端按查看者的
选择打开视频（它们是设置，不是输入）。

**全彩（4:4:4）。** 查看窗口的状态栏有一个“全彩”开关。打开且控制端能以 4:4:4 解码软件 VP9 或 AV1 时（当前每个版本都可以），
被控端把它们以全彩排在最前（I444：每个像素都有色度，因此一像素宽的彩色文字和线条保持清晰）并重新开始视频；关闭后恢复正常顺序。
全彩比 4:2:0 占用更多带宽与编码时间，视频流描述会注明它已开启（状态栏显示 “4:4:4”）。Windows ARM64 上的 libaom 构建时不含其
SIMD 代码（vcpkg 的移植），因此那里的 AV1 较慢；VP9 排在前面。

查看窗口打开时会请求关键帧；被控端随即重新说明视频流、其显示器与编码清单，并开始新的图像组。

## 画质与带宽

被控端运行 RustDesk 的视频 QoS（`core/third_party/rustdesk-qos`，包括其上游测试）：每秒在视频流中发送一次延迟探测，控制端会立即回传，
因此探测测量的是视频前方的队列，而不只是路径。回传结果、尚未回传的探测以及每秒发送的帧数共同决定帧率（从 15 提升到 30）
和画质系数；编码器的码率是 RustDesk 针对画面尺寸的基础码率乘以该系数（Balanced：0.67，1080p 下约 1.4 Mbit/s），并在运行中
调整。被控端还会每秒报告它测得的延迟以及选定的帧率与码率；查看窗口会显示延迟。

查看窗口的状态栏提供 RustDesk 的预设——更流畅（系数 0.5）、均衡（0.67）与更清晰（1.5）——15、30 或 60 的帧率上限，以及“全彩”开关；
它们以 `{"type": "quality", preset, fps, i444}` 发送到被控端，设置 QoS 中该查看者的画质与自定义帧率，以及是否使用全彩（见上文）。

被控端在统计信息中还报告其帧从画面到编码完成用了多久（`encode_ms`，上一秒各帧的平均值），其视频流描述说明它的编码器以及是否用
硬件运行（`encoder`、`hardware`，由编码器自己报告）。查看窗口数字的提示显示被控端用什么编码、本机用什么解码（例如“HEVC，
VideoToolbox 硬件”；AV1 总是 libaom 软件）、被控端的编码时间、网络延迟（即探测结果）、查看窗口自己的解码与绘制时间，以及帧率与
被控端目标帧率的对比。数字旁边的状态栏说明网络是直接到达该设备（直连）
还是经由服务器（中继，并提示在两台设备上都打开直接连接，[networking.md](networking.md)）。

## 声音

被控端把声音发给获得 `hear-sound`（单独的权限，控制端默认请求，正确密码默认授予）并提出请求的控制端（`{"type": "audio", on}`；查看
窗口在视频流开始时请求，恢复的控制端会再次请求）。共享哪种声音由被控端用户在设置的**共享的声音**中选择（界面的 `sound_source`，在
连接引擎时与改变时以 `sound.source` 发给引擎；助手会传给它的代理；正在进行的流立即切换）：本机正在播放的声音，或某一个输入设备
（`sound.devices` 列出它们：macOS 上是 Core Audio 中带输入的设备，Windows 上是活动的录音端点）。`audio.rs` 在 macOS 上通过只带声音的
主显示器 ScreenCaptureKit 流采集本机播放的声音（不含 Kyokai 自己的声音；“屏幕录制”权限即可），通过音频队列采集输入（“麦克风”权限：
两个应用都带有其用途说明与 `audio-input` 授权，选择输入时会请求它）；在 Windows 上通过 WASAPI 采集默认输出设备的回环或输入设备，按其
自身的格式。声音被转换为 48 kHz 立体声（采样率不同时线性重采样，单声道复制为双声道），以 Opus 的低延迟模式、96 kbit/s 编码为 10 毫秒
一包（`opus.rs`，libopus 由 vcpkg 构建；与 RustDesk 相同），静音半秒后不再发送，直到声音恢复（RustDesk 的零值门限）。助手模式下由会话
代理采集与编码，链路传送数据包。数据包作为以 `0x04` 开头的明文与视频并行传输，不计入视频的确认，发送画面期间到来的声音插在其分块
之间；会话落后时丢弃声音（被控端最多等待
半秒，控制端队列中最多 200 毫秒）。查看窗口在自己加载的核心中解码（`kyokai_audio_*`），通过 MyGo 的音频输出播放，并经过抖动缓冲：
开始时以及每次播放断了之后，它先攒够目标再放出声音，之后随到随放。目标从 80 毫秒开始，每当有声音到来时播放却断了一次（超过 300 毫秒
的停顿是被控端的静音，不算抖动）就增加 40 毫秒，最多 400 毫秒，连续 10 秒没有断时减少 10 毫秒，最少 40 毫秒；超出目标 60 毫秒以上
的声音从最早的开始削减到目标，使声音与画面同步。RustDesk 的每个数据包到达即播放，缓冲最多 3 秒，断时用 5 毫秒淡出，缓冲长时间超过
600 毫秒时才削减。栏中的
**声音**开关（未选择时打开，按设备保存）停止播放，并请被控端停止采集。在这台 Mac 上（2026-10-18），8 秒的观看收到 386 个数据包，即
7.7 秒的声音，与画面同时到达，输入列表列出了内置麦克风。

## 输入

只有被授予 `control-input` 的会话，查看窗口才会发送输入；被控端会再次检查。

| 事件 | 发送形式 |
|---|---|
| 指针移动、按下、松开 | `{kind: "pointer", action, button（0 主键，1 次键，2 中键）, x, y}`，x 与 y 是相对画面的比例；在画面周围黑边上的按下与移动会被丢弃，松开总会发送；没有按住按键的移动以 button 0 发送（被控端知道自己按住了什么）。查看窗口最多每 8 毫秒发送一次最新的移动，任何其他事件都会先发送正在等待的移动；会话落后时控制端引擎可能丢弃某次移动（随后还有更新的），其他事件都会等待会话接收 |
| 滚动 | `{kind: "scroll", dx, dy}`，以行计（触控板像素 ÷ 40）；`dy` 为正表示内容向下移动 |
| 映射或翻译模式下的按键 | `{kind: "scan", code, down, caps, num}`：按 Windows 的编号给出按键的扫描码（set-1 扫描码，扩展键为 0xE0xx，Pause 为 0xE11D），并附上控制端的 CapsLock 与 NumLock（[键盘模式](#键盘模式)） |
| 文字 | `{kind: "text", text}`：以 Unicode 字符输入，因此由控制端的键盘布局与死键决定（翻译与传统模式） |
| 传统模式：不带 Ctrl、Alt 或 Win、会产生文字的按键 | 不发送：随后会发送它的文字 |
| 传统模式：其他按键与快捷键 | `{kind: "key", key, down, mods}`，按名称发送（`enter`、`f5`、`page-down`、带 Ctrl 的 `c` 等）；只有发送过按下的键才会发送松开 |

被控端用 `SendInput` 注入：在所显示的显示器上做绝对移动（映射到虚拟桌面，因此位于主显示器左侧或上方的显示器也可用），扫描码按键用
`KEYEVENTF_SCANCODE`（0xE0 开头的扫描码带扩展键标志；Pause 按虚拟键），按名称的按键在导航键上带扩展键标志，并按每个按键的需要按下或松开修饰键，每个事件都
标记为 Kyokai 的（`dwExtraInfo`），以便与本地输入区分。不会向 Kyokai 窗口注入任何输入：落点下方是 Kyokai 窗口时丢弃指针的按下与移动，
指针下方是 Kyokai 窗口时丢弃滚轮，Kyokai 窗口拥有焦点时丢弃按键与文字；松开总会放行。Kyokai 的窗口不参与采集，因此只按焦点检查时，
Kyokai 那个看不见的窗口在前台时，查看窗口与模型能看到的其他窗口上的点击也会被拒绝。会话结束时会松开它按住的一切。格式错误的事件会被丢弃，但不会结束会话。

### 键盘模式

查看窗口提供 RustDesk 的三种键盘模式；在它的栏中选择的模式适用于所有查看窗口，并由 Kyokai
记住（未选择时为映射）。映射与翻译需要控制端抓取键盘：Windows 上用低级键盘钩子，macOS 上用事件监听（RustDesk 在那里的
抓取也是这样；需要控制端 Mac 上 Kyokai 的“辅助功能”权限，没有时查看窗口以传统模式工作并加以说明）。Mac 的事件监听在查看窗口
抓取期间取走发往 Kyokai 的按键，把 Mac 键码转换为 PC 扫描码，由被控端再映射回来（Command 即 Windows 键）；没有扫描码的按键
（Fn、媒体键）仍归这台 Mac，大写锁定键在 Mac 上只在切换时报告，因此作为一次按下与松开发送。只有 Kyokai 拥有最前面的窗口且查看窗口正在读取按键时，事件监听
才会取走按键（任一条件不满足时放行所有按键）；标签页被隐藏或连接已结束的查看窗口会结束它的抓取；事件监听随其线程关闭并失效（若留在
系统中，会让所有程序的键盘都失灵，直到退出 Kyokai）。画面获得焦点时会接收文字：macOS
只为接收文字的元素把按键变成文字，而传统模式把字母作为这些文字发送（缺少这一点时，Mac 上的字母都无法到达被控端）。传统模式下，
Mac 的菜单会在窗口看到之前取走 Cmd+C、X、V、A、Z 与 Shift+Cmd+Z；它们的编辑命令会重新作为这些快捷键发送。

**交换 Ctrl 与 Cmd**（任一端是 Mac 时显示在栏中，按设备记住）在查看窗口发送的内容中交换 Ctrl 与 Cmd（即 Windows 键）：包括按键
的修饰键，以及按位置发送的左右两侧按键。在 Mac 与 Windows 之间未选择时默认打开，因此 Mac 上的 Cmd+C 在 Windows 上是复制，
Windows 上的 Ctrl+C 在 Mac 上也是复制（RustDesk 有同样的开关，默认关闭）。按名称发送的按键在被控端带上它的修饰键，并随它一起
松开，输入文字时不按住任何修饰键（之前快捷键之后修饰键一直按着，随后输入的字母会带上 Ctrl 或 Cmd）。

| 模式 | 在控制端 | 在被控端 |
|---|---|---|
| 映射 | 画面拥有焦点且其窗口在前台时，核心中的低级键盘钩子在控制端的窗口看到之前按扫描码取走每个按键：Win、Alt+Tab、Alt+F4 与所有快捷键都送往被控端；CapsLock、NumLock 与 ScrollLock 也作用于控制端 | 每个按键按扫描码注入，因此由被控端的键盘布局决定输入的字符 |
| 翻译 | 在当前按住的修饰键下能在控制端键盘布局上产生字符的按键（死键也算；按着 Win，或只按着 Ctrl 或只按着 Alt 时不算）留给控制端，由它的键盘布局与输入法输入，并发送其文字；Shift、Ctrl、Alt 与锁定键两边都收到；AltGr 留在控制端；其他按键与快捷键都按扫描码取走 | 文字以 Unicode 输入，其他按键按扫描码注入 |
| 传统 | 如上所述的 GUI 工具包按键事件：没有 Win 键，没有被窗口占用的快捷键，不分左右修饰键，数字小键盘按其含义发送 | 按名称的按键与 Unicode |

抓取到的每个按键都附带控制端的 CapsLock 与 NumLock：与 RustDesk 的输入服务一样，被控端在字母键之前，
若自己的 CapsLock 不同就按一下 CapsLock；在含义受 NumLock 影响的小键盘按键之前同样处理 NumLock。Windows
自行生成的按键（随 AltGr 出现的 Ctrl、小键盘按键前后的 Shift）不会发送；被控端的键盘布局会生成它自己的。
抓取发送过按下的按键，会在其窗口离开前台、抓取结束或模式改变时松开；控制端上其他程序注入的按键不受影响。
钩子在第一次抓取时安装，在最后一次抓取结束时移除。Ctrl+Alt+Del 无法取走（Windows 不让任何钩子看到它）；
栏中的按钮在助手模式下发送它。

### 会话操作

拥有 `control-input` 时，查看窗口还提供 RustDesk 的会话操作；与输入一样，每个操作都会接管被控端的 AI 任务：

| 操作 | 在被控端 |
|---|---|
| 锁定屏幕 | 在用户会话中调用 `LockWorkStation`（助手模式下由代理调用） |
| Ctrl+Alt+Del | 仅限助手模式：助手作为 SYSTEM 服务调用 `SendSAS`；允许服务这样做的策略（`SoftwareSASGeneration`）只在调用期间打开，之后恢复原样 |
| 阻止对方的键盘和鼠标 | 只要有会话持有阻止，低级钩子就吞掉被控端自己的键盘和鼠标输入；Kyokai 注入的输入照常通过。被控端用户可用 Ctrl+Alt+Shift+Esc（同时停止 AI 任务）或任何钩子都看不到的 Ctrl+Alt+Del 解除；会话结束时也随之解除 |
| 隐私模式 | RustDesk 的隐私模式：一个覆盖整个虚拟桌面、可点穿、置顶且不参与采集（`WDA_EXCLUDEFROMCAPTURE`）的黑色窗口，被控端前的人看到的是黑屏，而画面中仍是屏幕内容；它同时阻止他们的键盘和鼠标，解除方式相同。Windows 无法让窗口不参与采集时会拒绝 |

被控端报告 Ctrl+Alt+Del 是否可用、阻止是否生效以及隐私模式是否开启；查看窗口的开关显示的是这份报告，而不是请求。

## 睡眠

有会话连接期间，被控端会让电脑与显示器保持唤醒（一个电源请求：“Kyokai: someone is connected”；助手模式下由会话代理在发送视频期间为显示器持有它，因为 Windows 不理会来自会话 0 的显示请求），因此空闲计时器既不会切断会话，也不会让被采集的显示器变暗。
电脑仍然进入睡眠时，进行中的 AI 任务会暂停（“电脑进入了睡眠”），等待有人恢复它；唤醒后，会话会像任何断线之后一样经由网络恢复。

## 剪贴板

会话拥有 `clipboard` 时，两端的引擎每秒查看两次各自的剪贴板（在 Windows 上只在其序列号变化时读取），把会话开始后复制的内容提供给对方，
对方将其放到自己的剪贴板上；以这种方式收到的内容不会再被送回。会话开始前剪贴板上已有的内容不会被提供，Kyokai 自己复制的文本（设备 ID、密码：在 Windows 上，
剪贴板的所有者是 Kyokai 的进程）也不会。支持最大 1 MiB 的文本，或以 PNG 发送、最大 3840×2160 的图片（最多 3 MiB；两者都有时优先文本；文件见“文件”）。
在助手模式下不接收来自控制端的图片，因为助手及其代理都有特权，从不解码远程媒体（[run-modes.md](run-modes.md)）。

### 文件

拥有单独的 `files` 权限时，在一端复制的文件和文件夹（在 Windows 上即资源管理器的文件列表 `CF_HDROP`）可以在另一端粘贴；
只有 `clipboard` 不传递文件，只有 `files` 也不传递文本。复制的一端列出所复制的内容——遍历文件夹，跳过链接与联接点——并提供每一项的路径与大小：
最多 1000 项、合计 1 GiB，超出的不会提供。另一端再次检查每个路径与限制后立即接受；它拒绝为空、为绝对路径、含 `.` 或 `..`、
含 Windows 名称中不允许的字符（`< > : " / \ | ? *`、控制字符）、以点或空格结尾、指向设备（`CON`、`NUL`、`COM1`、`LPT1` 等）或重复出现的路径。
随后复制的一端以每块最多 64 KiB 的方式逐个文件流式发送内容，按连接能接收的速度读取，因此不会把整个文件放进内存。
接收的一端把它们写入本次会话专用的文件夹（临时文件夹中的 `Kyokai\<random>`），全部到达后把这些文件放到自己的剪贴板上，
以便在任何地方粘贴。新的复制会取代正在进行的传输，发送期间大小发生变化的文件会结束其传输。
会话结束时该文件夹被删除；此前粘贴出去的文件留在粘贴的位置。

内容在提供被接受后立即传输，而不是在粘贴的那一刻：Windows 在粘贴的程序等待时向复制的程序索取延迟提供的数据，大的传输会让它卡住。

在助手模式下，代理读写剪贴板（管道上只传递路径列表），助手在模拟控制台上已登录用户身份的情况下读写文件，
因此以该用户的权限读取，并写入该用户的临时文件夹；没有用户登录时不共享文件。助手只搬运字节，从不解释它们。

## AI 任务

任务在被控端上运行，使用被控端的服务商密钥，操作被控端的主显示器。被控端用户在 AI 页面（或用
`kyokai-svc ctl ai-start`）启动任务。获得 `run-ai-task` 的控制端可以在查看窗口的 AI 面板中启动任务，并控制被控端的任务，无论由谁发起（被控端为所有控制端保留同一份 AI 记录）；下一条指令的草稿在那里与被控端的 AI 页面和其他每个控制端实时共享
（[protocol.md](protocol.md)，“AI 任务”）；拥有 `approve-ai-action` 时还可以答复这些任务的批准请求，而被控端用户也始终可以答复。
同一时间只有一个任务占用桌面，用同一个幂等键启动两次只会启动一个任务。

### 服务商

被控端用户设置**来源**（AI 页面的设置；`ai.json`）：每个来源有 id、名称、所用的模板、协议、基础 URL 以及从中使用的模型，任务使用某个来源中
选定的一个模型。新的被控端有两个来源：Claude（`https://api.anthropic.com/v1`）与 OpenAI（`https://api.openai.com/v1`）。模板还可添加 OpenRouter、
Google Gemini、Groq、Together、Fireworks、Deep Infra、Mistral、xAI、Moonshot、Z.ai / BigModel、阿里云百炼、SiliconFlow、火山方舟、MiniMax、
阶跃星辰、百度千帆、腾讯混元、NVIDIA NIM、Hugging Face、GitHub Models、Ollama、LM Studio 与 llama.cpp server（取自 MyApps-AI 的目录，
保留能接收图片和工具调用的 API；有多个站点的服务商按名称提供各站点）；自定义可以使用任意地址与协议。基础 URL 必须是 HTTPS，或只指向本机的明文 HTTP
（`localhost`、`127.0.0.0/8`、`::1`），因为截图会发往那里；这样的本机聊天服务器不需要密钥。每个来源的密钥是机密存储中的 `ai.<id>.key`，
移除来源时其密钥一并删除。**列出模型**只在用户要求时向来源查询模型（`GET <base>/models`；支持 OpenAI 风格、Ollama 与 OpenRouter 的列表，
不含嵌入、语音、图像与审核模型）；不会自行获取任何内容。

| 协议 | 使用者 | 请求 |
|---|---|---|
| `anthropic` | Claude | 带 computer 工具集的 Messages API（见下） |
| `openai-responses` | OpenAI | 带 `computer` 工具的 Responses API（见下） |
| `openai-chat` | 其他所有模板与自定义 | chat completions，把 Kyokai 的操作作为函数工具提供，名称与形式同 computer 工具集的成员（`left_click` 带 `coordinate`、`key` 带 `text`、`scroll` 带 `scroll_direction` 与 `scroll_amount` 等），因此三种协议共用一个解析器；屏幕以图片放在用户消息中，每个调用以一条 `tool` 消息答复，随后附上该批操作之后的屏幕；历史中只保留最新的 3 张截图。模型必须能接收图片并调用工具 |

模型按 OpenRouter 的写法显示为 `厂商: 模型`（`Anthropic: Claude Opus 5.5`、`Qwen: Qwen2.5 VL 72B Instruct`），经由其他来源访问的模型后面附上来源；
名称来自服务商自己的列表，或按规则由 id 得出（MyApps-AI 的命名规则，移植在 `internal/gui/modelname.go` 中）。

| | Claude | OpenAI |
|---|---|---|
| 请求 | Messages API 加 `computer_toolset_20260801`，自适应思考并返回进度说明，effort 为 `high`，服务端回退，输入超过 100,000 token 后由服务端清除旧的工具结果（保留最新 5 个） | Responses API 加 `computer` 工具，`previous_response_id`，`truncation: "auto"`，每次请求都带上指令 |
| 回复 | 每个操作一个 `tool_result`；历史只追加 | 每个调用一个 `computer_call_output`，附上该批操作之后的屏幕，并用一条说明列出失败或未执行的操作；安全检查只在被控端用户批准后才确认 |
| 默认模型 | `claude-opus-5-5` | `gpt-6.1-sol` |

请求经 HTTPS 发出（rustls，ring 提供方，系统根证书），每次最长五分钟，遇到过载和服务端错误时重试三次。显示给用户的错误绝不包含密钥。

### 截图与操作

被控端用 RustDesk 的 GDI 采集器按显示器的像素尺寸采集主显示器（采集线程按显示器感知 DPI），用平均法缩放到
1366×768 以内，以 PNG 发送。放大查看会裁剪一次新的采集，且绝不放大。坐标以最近一张完整截图为准；被控端把它们映射到显示器上，
经上文的输入服务注入，同样不进入 Kyokai 窗口并带有标记。

| 操作（`kind`） | 字段 | 执行方式 |
|---|---|---|
| `screenshot`、`zoom` | 放大查看时为 `region` | 一次采集，返回给模型 |
| `cursor-position` | — | 指针在截图像素中的位置，以文本返回 |
| `move` | `to`、`held` 键 | 按下修饰键，移动指针 |
| `click` | `at`（或指针位置）、`button`、`count`、`modifiers` | 先移动，再按下并松开（重复时间隔 40 ms） |
| `mouse-down`、`mouse-up` | `button` | 在指针位置按下或松开 |
| `drag` | 点的 `path`、`modifiers` | 按下，每段移动八次、间隔 10 ms，松开 |
| `scroll` | `at`、`dx`、`dy`（每格 120）、`modifiers` | 滚轮格数 |
| `type` | `text` | Unicode 文本，每 30 ms 一个字符（Windows 11 记事本等应用会把更快的连串输入弄乱）；每个换行按一次 Enter |
| `key-combo` | `keys`、`repeat` | 按组合中的修饰键按下各键 |
| `hold-key` | `keys`、`duration_ms` | 按下、保持、松开 |
| `wait` | `duration_ms` | 暂停 |

每个操作之前，被控端会检查：它能被解析；它的点位于最近一张截图之内；它的限制（文本最多 16 KiB，最多重复 100 次，等待和按住最长
300 秒，最多 100 格，拖动最多 256 个点）；屏幕尺寸仍与那张截图一致（否则操作已过时并被拒绝）；以及是否需要被控端用户批准。
第一个失败会结束本轮：其后的操作都回复为“未执行”。每个操作结束时都会松开它按住的一切。

批准方式为“被标记的步骤”（默认）或“每个操作”。前者在服务商为本轮提出安全检查时询问（在本轮第一个操作前询问一次），以及对使用
Windows / Command 键的快捷键询问。被拒绝的操作以“The host user declined this action”失败，模型从这里继续。

### 状态

| 事件 | 起始状态 | 结束状态 |
|---|---|---|
| 暂停（被控端用户、本地输入、控制端、接管，或控制端的会话结束） | running、approval | paused |
| 继续 | paused | running |
| 取消（包括紧急停止） | running、approval、paused | cancelled |
| 操作需要批准 | running | approval |
| 被控端用户作出决定 | approval | running |
| 模型完成 | running、paused | done |
| 出错 | running、approval、paused | failed |
| 被控端用户回复 | done | running |

### 被控端用户永远优先

任务运行期间，低级键盘与鼠标钩子监视本地输入：任务最近一次获得桌面（启动、继续或某个操作获得批准）之后，任何不是 Kyokai 注入的事件。
按键、鼠标按钮或滚轮立即计入；指针移动要在 1.5 秒之后才计入，因此点击“继续”或“允许”后把手移开鼠标不算接管；任务等待批准期间，本地输入不计入。
本地输入会立即暂停正在运行的任务，无论模型正在思考还是操作正在执行；按住的键或按钮会被松开。控制端的人在查看窗口中使用键盘或鼠标时同样构成接管：
在其输入被注入之前任务就会暂停，而任务执行期间单纯的指针移动不会被注入。每次暂停与取消都会推进任务的输入租约：之后才到达的模型响应会被记录，
但其中的操作一个也不会执行；对它的回复要等继续之后才发出，告诉模型什么都没有执行、应先重新截图。取消还会丢弃正在进行的请求。
Ctrl+Alt+Shift+Esc（紧急停止，任务运行期间有效）、托盘中的“停止 AI 任务”以及 `ai.stop` 都会取消任务，停止引擎也一样。

### 历史与设置

状态目录中的 `ai.json` 保存各来源、选定的模型与批准方式（最初版本的文件——一个服务商以及 Claude 与 OpenAI 各一个模型——会读成两个默认来源）；
密钥保存在机密存储中（`ai.<source>.key`），不会再显示，除了发给各自的来源之外不发往任何地方。`ai-tasks.json` 保存已结束的任务——指令、模型的文字与进度说明、各个操作及其结果，绝不包含截图——最多
100 个；AI 页面可以清除它。已结束任务的对话保留在内存中，因此在引擎停止之前，回复可以让它继续。

## macOS

| 部分 | 方式 |
|---|---|
| 权限 | 采集需要“屏幕录制”，输入需要“辅助功能”，本地输入监视需要“输入监控”，另有机密存储的钥匙串项目（[security.md](security.md)）；引擎报告这些权限（状态中的 `permissions`）；图形界面在每个版本首次启动时请求，也可以通过权限卡片上的“允许”请求——隐私权限在图形界面自己的进程中请求（`kyokai_privacy_request`），这样提示属于应用本身，而授予应用的权限同样覆盖引擎（macOS 把引擎算作应用的一部分）；钥匙串经由引擎请求（`permission.request` `keychain`）。macOS 27 对两个进程都不弹出提示：点“允许”会打开相应面板，在其中打开 Kyokai 的开关（“辅助功能”面板在那里称为“设备控制与数据访问”），同时打开系统设置中的相应面板。“屏幕录制”的授权在 Kyokai 重新启动后才生效，权限卡片上的“重新打开 Kyokai”会先停止引擎再重启 |
| 显示器 | Core Graphics 的活动显示器，以点为单位，即其全局坐标的单位（Retina 显示器是其像素的一半）；主显示器即首选显示器 |
| 采集 | 显示器的 ScreenCaptureKit 流，按其像素尺寸缩放到 1920×1080 以内，BGRA，不含指针（查看窗口根据指针消息自己绘制），设置中“在屏幕采集中隐藏 Kyokai”打开时（默认）也不含 Kyokai 的进程与应用的窗口：界面在连接引擎时以及设置改变时把它告诉引擎（`capture.show`；助手模式下由助手转告其代理），正在进行的视频流立即换用新的过滤器，AI 截图也照此处理；画面不变时不发送；没有权限时被控端发送测试图案 |
| 编码 | 先用 VideoToolbox 的 H.264 与 HEVC（见上文），然后是软件编解码器（`vp9-sw`、`av1`、`vp8`） |
| 解码 | 查看窗口经 VideoToolbox 解码 `h264` 与 `hevc`，经 libvpx 与 libaom 解码软件编码 |
| 输入 | 在 HID 层投递并标记为 Kyokai 的 Core Graphics 事件：以点为单位的指针事件，带点击次数以支持双击与三击；滚轮刻度按行；按名称的按键与修饰键（`ctrl` → Control，`alt` → Option，`meta` → Command），附带所按住修饰键的标志；文本以 Unicode 输入；扫描码经对照表转换为 Mac 键码（Caps Lock 跟随控制端；Mac 没有 NumLock）。防护会查找该点下窗口的所有者（按键则查找最前面的普通窗口），丢弃发往本引擎或启动它的应用的事件 |
| 本地输入 | 只监听的事件监听器（输入监控）记录被控端用户的按键与移动，跳过 Kyokai 标记的事件，并监视 Ctrl+Option+Shift+Esc |
| AI 任务 | 每次截图用一个短暂的 ScreenCaptureKit 流以全分辨率采集主显示器，输入与监视相同 |
