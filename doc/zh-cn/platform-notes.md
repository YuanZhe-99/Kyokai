## Windows

于 Windows 11 ARM64 验证（Snapdragon 开发套件，2026-10-16；Go 1.27.2、Rust 1.99.1、未安装 Clang 组件的 Visual
Studio 2026）：

| 引擎 | `scripts/smoke.sh user` 通过：状态、密码、换密码、拒绝第二个引擎、关闭、重启 |

| 应用（x64 安装包） | 在模拟下以同一身份运行；窗口按系统深色主题渲染 |

| S1 EasyTier 可行性验证 | v2.7.0 进程内内嵌、无 TUN、无需管理员：经原版服务器双向数据面可用，白名单有效，可干净重启；UDP 打洞未测（对称型 NAT） |
| 引擎内的 EasyTier（2026-10-17） | 经标准公共服务器：10 秒内上线并获得 DHCP 地址；通过 STUN 得到 NAT 类型（此网络为对称型）；使用各自配置的两个引擎互相列出对方的设备 ID，经中继，约 36 ms |
| 会话（2026-10-17） | 两个引擎经标准服务器：错误密码在两端都记为密码错误而被拒绝；正确的临时密码会触发被控端确认，确认只授予查看屏幕，会话即以此权限连接；随后控制端成为受信任设备（“已知”）；固定密码同样可用；从控制端关闭会话会同时结束两端 |
| 身份备份（2026-10-17） | 备份 → 重置（新设备 ID）→ 用错误口令恢复被拒绝，用正确口令恢复后旧设备 ID、固定密码与受信任设备都回来了，网络重新连接 |
| 远程 x64 虚拟机（2026-10-17） | CI 构建的 x64 安装包按用户安装、无任何提示；其引擎经标准服务器加入网络（两端都是对称型 NAT，因此经中继，约 99 ms）；从本机到虚拟机的会话在虚拟机上触发确认，并以授予的子集权限连接；虚拟机节点重启后，会话在 7 秒内恢复，权限不变且无需再次确认 |
| 视频通道（2026-10-17） | 测试图案（320×180 原始 RGBA）经两个引擎与公共服务器的中继：4 fps、约 7.6 Mbit/s，即这条路径上中继的上限；视频流描述能到达，并会在关键帧请求时重发 |
| 会话操作（2026-10-17） | 已在代码中实现，并经内存会话测试：被控端只向拥有 `control-input` 的会话提供，用户模式下不提供 Ctrl+Alt+Del；线路名称正确。锁定、输入阻止与 Ctrl+Alt+Del 尚未在桌面上运行 |
| GDI 采集回退（2026-10-17） | 在本机上，对经 GDI 列出的显示器打开 RustDesk 的 GDI 采集器，得到显示器完整尺寸的画面（`the_gdi_fallback_captures_and_skips_unchanged_frames`）；尚未在没有桌面复制的机器上运行 |
| 屏幕视频（2026-10-17） | 本机 1920×1080 屏幕经 DXGI、Media Foundation H.264（软件编码器；第一帧之后即有输出）、两个引擎与公共中继，再由查看窗口的解码器解码：屏幕大多静止时 15.5 fps、约 1 Mbit/s，画面正确 |
| QoS（2026-10-17） | 经公共中继，被控端从 15 fps 起步，随探测回传提升到 30，并选用 Balanced 码率（1080p 下 1.39 Mbit/s）；探测延迟 100–280 ms（中继路径加视频队列）；“更流畅”预设加 15 fps 上限把码率降到 1.04 Mbit/s 并保持 15 fps |
| 监听重新绑定（2026-10-17） | 监听绑定之后 DHCP 地址又发生变化的被控端会不再接受会话；现在节点地址变化时监听会重新绑定 |
| AI 运行时（2026-10-17） | 经核心的 HTTPS 客户端，在合成屏幕上（模拟桌面，不注入任何输入）完成一次真实的 Claude 任务（`claude-opus-5-5`）：它点击 SAVE、等待、截图、确认结果后结束；工具集、工具结果清除与三个 beta 头都被接受。在本机上，GDI 采集得到 1920×1080 的主显示器（以 1365×768 发送），输入钩子安装成功；尚未在真实桌面上运行任务 |
| 来自控制端的 AI（2026-10-17） | 在会话测试中，两个引擎的核心（内存连接，被控端的 AI 使用模拟桌面与本地服务商替身）把控制端启动的任务从控制端批准并运行到结束；没有 `run-ai-task` 的会话被拒绝，控制被控端用户自己启动的任务也被拒绝。在本机的两个引擎之间经公共中继（协议 2），`ctl watch --text` 到达了被控端的运行时，后者因没有密钥而拒绝；没有 `run-ai-task` 的会话被拒绝。尚未在两台机器之间运行 |
| 剪贴板（2026-10-17） | 使用内存剪贴板的会话测试：会话开始后任一端复制的文本都到达了另一端，此前已有的内容没有，没有 `clipboard` 的会话不传递任何内容，210 KB 的文本分成多个部分传了过去（以前会导致会话结束），图片以 PNG 传了过去；系统剪贴板（arboard）尚未在两台机器之间验证 |
| 硬件 H.264（2026-10-17） | 本机的 “QCOM Hardware Encoder - H264”（异步）优先于 Microsoft 软件编码器被选用；第一帧之后即有输出，其码流可由 Microsoft 解码器解码，屏幕源经它输出 1080p。同时打开多个（并行测试）曾导致进程崩溃；现在每个进程只打开一个，用完即关闭，12 次并行测试均通过；尚未比较 CPU 占用 |
| 编解码器（2026-10-17） | 本机的 Media Foundation：H.264（GPU 与软件）、HEVC（GPU 与 HEVC 视频扩展）、VP9（VP9 扩展）编码器；H.264、HEVC 与 VP9 解码器。每种在 320×192 下都能往返；GPU 的 HEVC 在 720p 与 1080p 下无法解码（软件 HEVC 可以），因此被控端优先选 H.264。两个引擎之间，控制端提供了三种，被控端选了 H.264，查看窗口的解码器解出了 100 帧中的 90 帧 |
| 显示器（2026-10-17） | 本机只有一个显示器，因此不会发送列表，查看窗口也不提供选择；在显示器之间切换以及在第二个显示器上的输入，要等有两个显示器的机器来验证 |
| 跨网络的协议 2（2026-10-17） | 本机引擎经公共中继连接远程 x64 虚拟机（`e7447a4` 的 CI 构建）：会话拥有 `view-screen`、`run-ai-task`、`approve-ai-action` 与 `clipboard`；虚拟机的引擎（运行在其 SSH 会话中，没有桌面）发送测试图案，AI 请求到达了它的运行时并因没有密钥被拒绝 |
| 虚拟机的真实桌面（2026-10-17） | Kyokai 在远程 x64 虚拟机的控制台会话中启动（`f928338` 的 CI 构建），本机引擎作为控制端经公共中继连接，授予全部五项权限：1280×720 桌面以 H.264 传输，空闲屏幕下 8 秒 23 帧（有变化才发送），解码 20 帧，快照与屏幕一致；剪贴板文字双向、虚拟机上 64×48 的图片都原样到达。控制端发起的 Claude 任务（`claude-opus-5-5`）第一次点击被拒绝：Kyokai 自己的窗口拥有焦点，但它不参与采集，模型看不到它。改为按指针下方的窗口检查指针输入后，同样的情况下任务从任务栏搜索打开了记事本并输入了文字；Windows 键快捷键按“标记”策略请求了批准。在 Windows 11 记事本中输入的文字起初出错（“Hello iiiiiiiiiii”，之后又漏掉一个字母），由模型自行改正，因此那里的文字注入还不可靠。本地 API 拒绝来自 SSH 登录的 `ctl`：引擎无法打开该进程读取其身份，因此按失败关闭处理。关闭“在屏幕采集中隐藏 Kyokai”后（保存的偏好，然后重启），主窗口的显示亲和性为 0，Kyokai 自己的视频中能看到该窗口，临时密码仍被遮盖；那里没有实际点击这个开关 |

| 助手（2026-10-17） | 在本机上，经用户同意：`helper install` 通过一次 UAC 提示把文件复制到 Program Files，创建 `ProgramData\Kyokai`（其中 `state` 对用户关闭），并启动 `KyokaiHelper`；助手引擎运行在会话 0，代理以 SYSTEM 身份运行在会话 1；操作者在 `ctl.sock` 上得到服务，机密以 SYSTEM 身份保存在 DPAPI 中。`ctl move` 把一个测试身份及其别名、网络与固定密码迁入，之后又迁出（每次源引擎都停止；干净退出后服务保持停止）。没有界面连接时，后台服务以 `absent` 拒绝临时密码，而让拥有无人值守授权、使用固定密码的受信任设备无需确认即可进入。视频来自代理，1920×1080 H.264（64 帧中解码 58 帧），安全桌面上的 UAC 提示也出现在其中；未尝试在那里输入。`helper.update` 拒绝了未签名的 bundle。`helper uninstall --purge`（第二次提示）之后没有留下服务、文件夹或进程。发现并已修复：迁入存储会重建核心，而核心忘记了服务对象，转而请求确认（尚未用助手重新运行）。第二次运行（修复后的核心、直接连接、添加并删除防火墙规则）：一个 UAC 提示在无人触碰的情况下在安全桌面上保持了 6 秒，控制端经代理发送的点击关闭了它。自我停用：应用文件夹消失后约 2 分钟，助手删除了自己的服务与防火墙规则并退出，其文件留待下次重启时删除；第一次尝试中途停止，因为它自己打开的日志阻止了删除状态（已修复：无法立即删除的内容在重启时删除） |
| 防火墙提示（2026-10-17） | 直接连接关闭时，从新路径启动的引擎在启动时仍会在所有地址上短暂打开两个 UDP 套接字（STUN），Windows 防火墙因此询问；把 STUN 也关闭后，它只保持到服务器的出站 TCP 连接，从启动起采样 15 秒没有任何 UDP 套接字，并经中转上线 |

## 已知限制

- 在开发机上，`AppData\Local` 或 `AppData\Roaming` 下文件夹中创建的 AF_UNIX 套接字文件在监听关闭后会残留为无法访问的条目，
  导致再次绑定失败；`%TEMP%` 与用户文件夹表现正常。因此引擎的套接字放在 `%TEMP%\kyokai`。残留条目
  （`AppData\Local\kyokai` 与测试文件夹）无法在创建它们的会话中删除。
- `ring`（EasyTier、TLS 客户端、`cargo-deny`）在 Windows ARM64 上需要 clang：VS 组件把它装在 `VC\Tools\Llvm\ARM64\bin`，
  但不会加入 `PATH`。
- Windows 安装包没有代码签名；首次启动时 SmartScreen 会警告。
